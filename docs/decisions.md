# 기술 결정 기록

> 중요한 기술 결정을 쌓아 두는 곳. 새 결정은 아래에 추가하고, 바뀐 결정은 지우지 않고 "대체됨"으로 표시한다.

## ADR-001 모듈러 모놀리스

- **날짜**: 2026-10-14
- **결정**: 웹사이트 1개, 서버 1개, DB 1개. 코드 안에서 `sales`, `customer`, `product`, `common` 모듈로 나눈다.
- **맥락**: 1인 개발, 8주, 월 운영비 0원. 판매(매장 업무)와 고객관리는 성격이 달라 경계를 나누고 싶다.
- **대안**: (1) 모놀리스 한 덩어리 (2) 마이크로서비스 2개 이상
- **이유**: (1)은 판매와 고객 코드가 뒤엉킨다. (2)는 배포·운영 부담이 두 배이고 비용이 든다. 모듈러 모놀리스는 경계는 지키면서 운영은 하나로 한다.

## ADR-002 판매 → 고객관리 연결은 outbox 이벤트

- **날짜**: 2026-10-15
- **결정**: 판매·반품 저장과 같은 트랜잭션에서 `outbox_event`에 이벤트를 기록하고, 발행기가 고객 모듈에 전달한다. 고객 모듈은 `processed_event`로 중복 처리를 막는다.
- **맥락**: 판매가 저장되면 고객 구매 기록과 등급이 바뀌어야 한다. 고객 쪽 처리가 실패해도 판매는 성공해야 한다.
- **대안**: (1) 판매 서비스에서 고객 서비스를 직접 호출 (2) Spring 메모리 이벤트만 사용 (3) Kafka 같은 메시지 브로커
- **이유**: (1)은 고객 쪽 실패가 판매까지 실패시킨다. (2)는 서버가 죽으면 이벤트가 사라진다. (3)은 1인·0원 조건에 과하다. outbox는 DB 하나로 "이벤트 유실 없음"과 "재시도"를 얻는다.

## ADR-003 모듈 간 FK 없음, 고객 모듈은 구매 기록 사본 사용

- **날짜**: 2026-10-15
- **결정**: 모듈끼리는 ID만 참조하고 FK를 걸지 않는다. 고객 모듈은 판매 테이블을 조인하지 않고, 이벤트로 받은 `customer_purchase`를 쓴다.
- **맥락**: 모듈 경계를 코드뿐 아니라 DB에서도 지키고 싶다.
- **대안**: 모든 테이블에 FK, 판매 테이블 직접 조인
- **이유**: 판매 테이블이 바뀌어도 고객 모듈이 깨지지 않는다. 나중에 모듈을 떼어낼 때 FK부터 풀 필요가 없다. 대신 데이터가 일부 중복되고, 정합성은 이벤트 처리로 보장해야 한다.

## ADR-004 등급 상태를 3개 컬럼으로

- **날짜**: 2026-10-15
- **결정**: `customer_summary`에 `computed_grade`, `current_grade`, `confirmed_grade`를 둔다.
- **맥락**: 등급 규칙이 "승급은 즉시, 강등은 매월 정기 산정, 반품 시 승급 취소(확정 등급 아래로는 안 내려감)"이다.
- **대안**: 등급 1컬럼 + 이력 테이블에서 계산
- **이유**: 1컬럼으로는 반품 취소의 하한(마지막 확정 등급)을 매번 이력에서 찾아야 한다. 3컬럼이면 규칙이 조건문 3줄이 되고 테스트가 쉽다.

## ADR-005 쿠폰 대신 등급 할인

- **날짜**: 2026-10-15
- **결정**: 쿠폰 기능을 만들지 않는다. 판매 라인마다 할인율(%)을 두고, 회원은 현재 등급 할인율(0~5%)이 자동 적용된다. 직원은 상한 안에서 수정할 수 있다. 비회원은 할인이 없다.
- **맥락**: 판매 시 할인이 필요하다. 남은 시간은 빠듯하다.
- **대안**: (1) 매장 공용 쿠폰 (2) 고객별 발급 쿠폰 (3) 할인 없음
- **이유**: 쿠폰은 발급·사용·부분 반품 배분까지 새 도메인이라 10~15시간이 든다(추정). 등급 할인은 기존 테이블에 컬럼만 더하면 되고(3~5시간), 등급이 곧 혜택이 되어 CRM의 목적과 맞는다. 비회원 할인을 막으면 고객등록을 유도할 수 있다. 할인이 라인 단위라 부분 반품 환불 계산도 단순하다.

## ADR-006 판매 중복 요청 방지 키는 `sale` 컬럼에

- **날짜**: 2026-10-15
- **결정**: `POST /sales`는 `Idempotency-Key` 헤더를 받아 `sale.idempotency_key`(UNIQUE)에 저장하고, 요청 본문 해시를 `sale.request_hash`에 저장한다. 같은 키가 다시 오면 저장된 판매로 응답을 다시 만들고, 해시가 다르면 `409`로 거절한다.
- **맥락**: 버튼을 두 번 누르거나 네트워크가 재전송해도 판매가 두 번 생기면 안 된다. 확정된 ERD에 저장 위치가 없었다 (03-api.md 작성 중 발견).
- **대안**: (1) 별도 멱등 키 테이블(키, 요청 해시, 응답 본문) (2) 저장하지 않고 화면에서 버튼만 막기
- **이유**: (1)은 판매 1건 = 키 1개인 이 시스템에서는 과하고 응답 본문까지 저장해야 한다. (2)는 네트워크 재전송을 못 막는다. `sale` 컬럼이면 판매 저장과 같은 트랜잭션에서 UNIQUE 제약이 동시 요청까지 막는다. 대신 판매 외 API에 멱등이 필요해지면 그때 테이블로 옮긴다.

## ADR-007 같은 판매의 이벤트는 순서대로 처리

- **날짜**: 2026-10-15
- **결정**: outbox 발행기는 `PENDING`을 오래된 순으로 읽되, 같은 `aggregate_id`(판매)의 앞 이벤트가 `PUBLISHED`가 아니면 뒤 이벤트를 건너뛴다. 1초마다 읽고, 최대 10회 재시도 후 `FAILED`로 둔다.
- **맥락**: `SALE_COMPLETED` 처리가 실패해 재시도를 기다리는 동안 같은 판매의 `SALE_RETURNED`가 먼저 처리되면, 고객 모듈이 아직 없는 구매 기록을 반품하게 된다.
- **대안**: (1) 순서 무시, 고객 모듈이 없는 구매 기록의 반품을 보관했다가 나중에 적용 (2) 전체 이벤트를 한 줄로 처리(앞이 실패하면 전부 멈춤)
- **이유**: (1)은 고객 모듈에 보류 상태와 재적용 로직이 생긴다. (2)는 한 건 실패로 모든 매장의 등급 반영이 멈춘다. 판매 단위 순서 보장은 인덱스 하나(`aggregate_id, created_at`)로 해결되고, 실패 영향이 그 판매에만 머문다.

## ADR-008 고객 요약을 매일 새벽 다시 계산

- **날짜**: 2026-10-15
- **결정**: 매일 새벽 전체 고객의 최근 12개월 집계와 `computed_grade`를 다시 계산한다. `current_grade`와 `confirmed_grade`는 바꾸지 않는다.
- **맥락**: `customer_summary`는 이벤트와 월 정기 산정 때만 갱신된다. 그 사이 12개월 밖으로 빠진 구매가 집계에 남아, 고객 상세의 12개월 금액과 '실적 기준 등급'(GRD-03)이 틀리게 보인다.
- **대안**: (1) 조회할 때마다 12개월 집계 (2) 낡은 값을 한계로 문서에만 명시
- **이유**: (1)은 요약 테이블을 둔 이유(ERD 결정 3)와 반대다. (2)는 직원에게 틀린 등급 근거를 보여준다. 고객 5천 명이면 하루 한 번 재계산은 가볍다. 시간이 지나면 실적은 줄기만 하므로 이 작업은 승급을 만들지 않고, 강등은 BR-05대로 정기 산정에서만 일어난다.

# 시스템 아키텍처 점검 (2026-10-30)

> 대상: [04-architecture.md](04-architecture.md), 그림 [images/architecture.png](images/architecture.png). 기준: 01 비기능 요구사항, 03, [decisions.md](decisions.md), 실제 설정(`build.gradle`, `application.properties`, `docker-compose.yml`, `backend-ci.yml`).
> 방법: ① 요구사항(기능·업무 규칙·NFR)마다 맡는 모듈과 막아 주는 장치가 있는지 ② 운영 시나리오(서버가 잠듦, 6월 수동 실행, 자정 직전 판매, 퇴사 처리, 처리 실패, 리뷰어 실행) ③ 문서와 실제 설정 대조.
> 상태: **초안**. 사용자 결정(2026-10-30)으로 아래 항목은 지금 정하지 않고, "처리할 작업"을 할 때 정해 04·ADR에 반영한다. 정하면 "결정" 칸을 채운다.

## 1. 통과한 것

| 확인 | 결과 |
| --- | --- |
| 모듈 의존 방향 | 순환 없음. 판매 → 상품·고객(api 읽기, outbox 쓰기), 모두 → 공통, 공통 → 고객은 이벤트만, 고객·공통 → 판매 없음 |
| 이벤트 | 판매와 outbox를 한 트랜잭션에, `processed_event`로 중복 처리 방지, 처음 판매 단위로 순서 보장 |
| 동시성 | 영수증 번호 잠금, 남은 수량 잠금(ADR-030), 요청 키 UNIQUE |
| 비기능 | NFR-01(이름 인덱스·요약 테이블), 02(1초 발행), 02a(MyBatis 일괄), 03·03a, 04~07(암호화, 로그는 ID만, 비밀 값은 환경변수), 12, 13 |
| 문서와 실제 설정 | Boot 4.1.1, Java 21, MariaDB 11, `ddl-auto=validate`, `open-in-view=false`, compose utf8mb4 — 04 9장과 맞음 |

## 2. 정할 것

| # | 중요도 | 문제 | 추천 | 처리할 작업 | 결정 |
| --- | --- | --- | --- | --- | --- |
| A1 | 높음 | **시간대가 정해져 있지 않다.** 하루 마감 자정, 시즌 6/1 0시, 판매 시각 "오늘 0시 이후", 7/1 확정, 할 일 만기일이 모두 한국 시간 기준인데 무료 서버는 보통 UTC다 | "지금"은 주입한 `Clock`(Asia/Seoul)으로만 읽는다. DB에는 한국 시간으로 저장하고 SQL에서 `NOW()`를 쓰지 않는다(시각은 값으로 넘김). 테스트는 고정 시계로 자정·시즌 경계를 재현한다. 새 ADR | B0-6 (첫 코드 전에) | |
| A2 | 중간 | **정기 산정과 이벤트 처리가 동시에 돌 수 있다.** 6월 수동 실행 중 판매가 들어오면 같은 고객 요약을 양쪽이 고쳐 한쪽 값이 덮어써질 수 있다 | 정기 산정은 어디서 시작하든(새벽, 서버 시작, 수동) outbox 발행기와 같은 스케줄 스레드 1개에서 차례로 돈다. 그동안 반영이 늦는 것(최대 30초)은 받아들인다 | B3-4 | |
| A3 | 중간 | **퇴사 이관 응답의 "옮긴 고객 수"를 common이 알 수 없다** (03 4.11). 이벤트는 값을 돌려주지 않고, common이 고객 모듈을 부르면 순환이다 | 이관 이벤트에 결과 칸을 두고 고객 모듈 리스너가 같은 트랜잭션에서 채운다(`@EventListener`, 커밋 뒤에 도는 방식 아님). ADR-024 변경 | B4-6 | |
| A4 | 중간 | **배포할 곳이 정해지지 않았고 MariaDB가 걸림돌이다.** 무료 DB는 PostgreSQL이 많은데 설계는 MariaDB 동작(`FOR UPDATE`, JSON, UNIQUE)에 기댄다 | 선택 기준: MariaDB 또는 그대로 도는 MySQL 호환, 월 0원, 잠드는지, 앱과 DB를 같은 곳에. 후보는 "무료 VM에 compose로 앱+DB" 또는 "앱 호스팅 + MySQL 호환 무료 DB" | B0-4 (6단계) | Oracle 무료 VM 1대에 compose로 앱+MariaDB 11. DB 포트는 VM 안에만 (ADR-033, 11/12) |
| A5 | 낮음 | `spring.sql.init.mode=always`라 기본 데이터 SQL이 켜질 때마다 다시 들어간다(중복). `schema.sql` 변경은 이미 있는 배포 DB에 반영되지 않는다 | 기본 데이터는 `INSERT IGNORE`로 여러 번 돌아도 같게. 배포 DB는 12단계 전에 스키마를 확정한 뒤 만든다 | B0-6, 12단계 | |
| A6 | 낮음 | NFR-11은 "`docker compose up` 한 번으로 실행"인데 지금 compose는 DB만 띄운다 | B0-4의 Dockerfile을 compose에 `app`으로 넣는다. 리뷰어는 한 번에, 개발은 지금처럼 `bootRun` | B0-4 | compose에 `app` 서비스를 더한다 (ADR-033, 11/12) |
| A7 | 낮음 | 테스트 DB가 두 갈래다. 문서는 Testcontainers, CI는 GitHub의 MariaDB 서비스 | Testcontainers로 바꾸면서 CI의 DB 서비스를 지운다. 그 뒤 `./gradlew test`는 Docker만 있으면 된다 | B0-6 | |

| A9 | 낮음 | 고객 목록 20명마다 직원 이름을 common에 하나씩 물으면 느려진다(N+1). 판매 내역·영수증의 고객 이름(sales → customer), 판매 사원·매장 이름(sales → common)도 같다 (2026-11-05 화면 대조) | 각 모듈 `api`가 "ID 목록 → 이름"을 한 번에 주는 조회를 둔다 (NFR-01, 03 4.12) | B1-5, B2-2 | |

## 3. 요구사항 대조 (2026-10-30)

01의 기능·업무 규칙을 맡는 모듈과 그림의 상자에 하나씩 대 봤다. '다음'·'나중' 단계는 끼울 자리가 있는지만 봤다.

| 요구사항 | 맡는 곳 | 결과 |
| --- | --- | --- |
| SAL-01~08 판매·반품·교환·정정·마감 | sales (STORE만, 판매 사원은 common, 고객·상품은 api 읽기, outbox) | ✓ |
| SAL-04 응대 메모 | sales → 이벤트 → customer 구매 메모 | ✓ |
| REG-01~06 고객 등록 (직원·iPad·QR) | customer, 공개 API·요청 수 제한·키오스크 권한은 Security | ✓ 그림의 customer 상자에 "고객 등록"이 빠져 있어 더함 |
| REG-07 SMS 인증 (다음) | 끼울 자리 없음 | △ A12 |
| CUS-01~05 | customer (구매이력 CUS-03은 sales가 제공) | ✓ |
| GRD-01~06 | customer, 정기 산정은 스케줄 작업 | ✓ (시간대 A1, 동시 실행 A2) |
| MEM-01~03, CAL-01·02·06·07 | customer (오늘 할 일은 만기일로 조회, 스케줄 없음) | ✓ |
| CAL-09 알림함 / CAL-08 폰 푸시(다음) | common 알림 인터페이스 (ADR-029) | ✓ |
| PRD-01·02 | product (엑셀은 Apache POI) | ✓ |
| AUTH-01~04 | Security + common 계정 (11단계, 그 전엔 로그인 계정 자리 ADR-032) | ✓ |
| ADM-01 직원 관리·이관·QR | common → 같은 트랜잭션 이벤트 → customer, QR은 common(ZXing) | ✓ 그림의 common에 "QR 이미지"를 더함, 이관 결과 수는 A3 |
| ADM-03 매장 목록 | common + sales의 매장별 판매 요약(화면이 합침) | ✓ |
| ING-01 더미 판매 | `seed` 프로필 | ✓ |
| BR-05·14·16 날짜 규칙 (6/1, 7/1, 자정, 만기일) | 날짜로 판단, 스케줄 없음 | ✓ (시간대 A1) |
| BR-06 이벤트 재시도·`FAILED` | outbox 발행기 | ✓ 되돌리는 절차는 A11 |
| BR-15 퇴사 이관 | common → customer 이벤트 | ✓ (A3) |
| 범위 밖 (재고, 결제, POS·ERP 연동, 고객 앱) | 그림에 없음 | ✓ |

그림에서 계정·기기 5개(매장 계정, 직원, 본사, 키오스크, 고객 QR)와 할 수 있는 일은 01 2장과 맞다.

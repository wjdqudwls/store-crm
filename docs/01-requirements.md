## 1. 범위 요약

- 단일 브랜드, 여러 매장. 웹사이트 1개, 서버 1개, DB 1개 (모듈러 모놀리스). 여러 브랜드는 나중에 `brand_id`로 나눈다 (ADR-028).
- 모듈 구성

| 모듈 | 메뉴 | 역할 |
| --- | --- | --- |
| `sales` | 매장 업무 › 판매 기록, 판매 내역, 하루 마감 | 판매·반품·교환·정정·기록 취소, 하루 마감, 판매 이벤트 발행 |
| `customer` | 매장 업무 › 고객등록 / 고객관리 전체 | 고객, 가족 구성원, 구매이력, 등급, 상담 메모, 콜리스트, 후속 연락, 담당 고객 이관 처리 |
| `product` | 매장 업무 › 상품 관리 | 상품 등록(선택)·엑셀 가져오기·조회 |
| `common` | 로그인, 본사 › 매장 목록·상세 | 인증, 매장, 직원(직급·메인/임시 매니저)·키오스크 계정, 직원 알림함 |

- 범위 밖: 재고(나중), 결제 연동(나중), POS·ERP 연동(나중), 고객 앱·메신저(나중), SCM(나중, 별도 서비스).

## 2. 사용자와 권한

| 계정 | 누구 · 기기 | 할 수 있는 일 |
| --- | --- | --- |
| `HQ` 본사 | 본사 담당(작은 브랜드는 대표). PC 웹 + 폰 웹앱 | 매장 목록·상세, 전 매장 조회. **접근 제한이 필요한 일 전부**: 직원·키오스크 계정 관리(등록·비활성화·이관·승격·비밀번호), 매장 계정 비밀번호, 마감된 판매 정정, 하루 마감 다시 열기, 등급 기준, 후속 연락 설정, 정기 산정 수동 실행. 판매는 기록하지 않는다 |
| `STORE` 매장 계정 | 매장 노트북·매장폰. 매장 직원 모두가 쓰는 공용 계정 | 판매 기록(판매 사원 선택)·그날 정정·기록 취소, 반품·교환, 하루 마감, 고객 등록·조회·수정(가족 포함), 상담 메모·연락 결과(직원 선택), 콜리스트·오늘 할 일(매장 전체), 상품 등록·조회, 등급 기준 조회 |
| `MANAGER`·`SENIOR`·`JUNIOR`·`STAFF` 직원 | 매장 직원 본인. 폰 웹앱 | 내 할 일, 고객 조회, 콜리스트(기본: 내 담당), 상담 메모, 알림함. 판매는 기록하지 않는다 |
| `KIOSK` | 매장 iPad (매장별, 본사가 만든다) | 고객 등록 폼만 (REG-02). 호출할 수 있는 API는 등록, 내 정보 조회(`GET /me`), 공개 API뿐 |

- 고객은 로그인 없이 등록 폼만 쓴다 (매장 iPad 또는 QR, REG-02·03).
- **직급**: 매장 안의 순서는 매장 계정 > 매니저 > 시니어 > 주니어 > 스태프다. 직급은 퇴사 이관 규칙과 매니저 수에만 쓰고(BR-15), 판매·고객·콜리스트 권한은 직급마다 같다. 매니저는 매장마다 **메인 1명 + 임시 1명**까지다. `STAFF`는 맨 아래 직급(스태프)이고, 예전 문서의 STAFF(매장 직원 전체)와 다르다.
- **판매 매장은 매장 계정의 소속 매장이다.** 요청으로 매장을 받지 않는다. 본사 계정은 판매를 기록할 수 없다 (03-api.md `STORE_REQUIRED`).
- **누가 했는지**: 매장 계정은 여러 사람이 쓰므로 판매·연락 결과·메모를 남길 때 직원을 고른다 (기본값은 직전에 고른 직원). 접근 제한 기능은 본사 개인 계정으로 하므로 사람 단위로 남는다.
- **기기 계정과 개인 계정**: 매장 계정과 키오스크는 기기에서 계속 로그인 상태로 둔다. 본사와 직원은 개인 계정이다 (AUTH-03).
- 조회 범위: 고객은 여러 매장에서 사므로 브랜드 전체 고객을 조회한다. 판매 내역은 매장 계정은 자기 매장, 본사는 매장을 골라서 본다.
- 본사 화면은 매장 목록에서 매장을 골라 들어가고, 매장마다 바꿀 정보(직원, 판매 정정, 하루 마감, 매장 계정)는 매장 상세에서 다룬다 (ADM-03). 매장 추가 화면은 다음 단계다 (ADM-02).
- 매장 매니저 전용 권한(자기 매장 직원 관리 등)은 다음 단계다.

## 3. 기능 요구사항

### 3.1 매장 업무: 판매 (SAL)

| ID | 기능 | 상세 | 단계 |
| --- | --- | --- | --- |
| SAL-01 | 판매 기록 | 고객의 구매를 기록한다. 결제는 매장의 ERP·POS에서 따로 하고, 이 기록은 고객관리를 위한 것이다. **매장 계정(매장 노트북)에서** 기록한다. 판매 사원 선택(필수, 기본값은 직전 선택) → 고객 선택(생략 가능, BR-07) → 상품 고르기(등록 상품을 상품명·품번으로 검색 → 색상·사이즈) 또는 직접 입력(상품명·제품유형·사이즈) → 수량 → 결제 금액(BR-10) → 착용자(가족 구성원, 선택, BR-13) → 판매 시각(기본은 지금. 바쁠 때 몰아서 입력할 수 있게 **오늘 0시 이후, 지금보다 이른 시각**을 고를 수 있다. 다른 날짜와 미래는 안 된다) → 저장 전 확인 창(판매 사원·고객·상품·결제 금액 요약과 "구매 기록을 저장할까요?") → 저장하면 "○○님 구매이력이 저장되었습니다". 결제는 이 서비스에서 하지 않으므로 "결제" 표현은 쓰지 않는다. 판매 매장은 매장 계정의 소속 매장(2장). 마감된 날에는 기록할 수 없다 (BR-16). 영수증 번호 자동 발급(`매장코드-판매일자-순번`, 예: GN01-20261015-0012). 저장 버튼을 두 번 눌러도 판매는 한 건만 생긴다 (BR-12) | MVP |
| SAL-02 | 판매완료 이벤트 | 판매 저장과 같은 트랜잭션에서 이벤트를 기록하고, 고객관리 모듈에 전달한다 (BR-06) | MVP |
| SAL-03 | 반품 | 원 판매를 지정해 라인 단위로 반품 → 반품 이벤트 발행. 남은 수량보다 많이 반품할 수 없다. 마감된 날에는 새로 기록할 수 없다 (BR-16). 환불 금액은 BR-11, 중복 저장 방지는 BR-12 | MVP |
| SAL-04 | 응대 메모 | 판매등록 화면에서 메모를 쓰면 판매와 함께 저장되고 고객의 상담 메모(유형 '구매')에 남는다. 비회원 판매에는 메모 입력란을 보이지 않는다 | MVP |
| SAL-05 | 판매 내역 | 기간별 판매 목록(매장 계정은 자기 매장, 본사는 매장을 골라서, 2장), 영수증 상세(라인, 판매 사원, 정가와 결제 금액, 반품·교환 내역). 기록 취소된 판매는 "기록 취소"로 표시하고, 정정·교환으로 생긴 판매는 원 판매와 연결해 보여준다 | MVP |
| SAL-06 | 교환 | 원 판매의 라인 일부를 반품하고 새 상품을 한 번에 기록한다. 금액 차이(추가 결제·차액 환불)는 그대로 남긴다. 새 상품은 새 영수증 번호를 받고 원 판매와 연결한다. 티켓은 BR-17, 후속 연락 할 일은 새로 만들지 않는다. 마감된 날에는 기록할 수 없다 | MVP (줄이는 순서 2단계) |
| SAL-07 | 판매 정정·기록 취소 | 판매한 날, 마감 전에는 매장 계정이 판매를 고치거나(연결 고객, 상품·사이즈, 수량, 결제 금액, 착용자) 통째로 기록 취소할 수 있다. 마감 뒤에는 본사(HQ)만 고친다. 정정은 원 판매를 기록 취소하고 원래 시각으로 다시 기록한다 (BR-16, ADR-026) | MVP (정정은 줄이는 순서 1단계) |
| SAL-08 | 하루 마감 | 매장 계정에서 "오늘 판매 마감"을 누르면 그날 판매가 잠긴다. 안 누르면 자정에 자동으로 잠긴다. 다시 여는 것은 본사(HQ)다 (BR-16) | MVP |

### 3.2 매장 업무: 고객등록 (REG)

종이 고객등록카드를 대신한다. **같은 등록 폼**을 세 곳에서 연다: 매장 iPad, 고객 본인 폰(QR), 직원 화면.

| ID | 기능 | 상세 | 단계 |
| --- | --- | --- | --- |
| REG-01 | 고객 등록 폼 | 필수: 이름(외국인은 영문 이름, REG-06), 전화번호, 내/외국인(`DOMESTIC`·`FOREIGN`, 기본 내국인), 개인정보 수집·이용 동의, 만 14세 이상 확인. 선택: 생년, 생일(월일), 주소(시/도, 구, **상세주소**), 성별(`F` 여성·`M` 남성), 선호 품목(복수 선택), 사이즈(상의/아우터/하의/신발, 허용값은 02-erd.md 3.2), 연락 채널(`CALL` 전화·`SMS` 문자·`KAKAO` 카톡), 마케팅 수신(문자/카톡 각각). 아우터·하의 사이즈 목록은 성별로 나뉘므로, 성별을 고르지 않으면 아우터·하의 사이즈 칸을 숨긴다 | MVP |
| REG-02 | 매장 iPad 등록 | 본사가 매장별로 만든 키오스크 계정(KIOSK)으로 iPad에서 로그인하면, 내 정보(`GET /me`)로 역할과 소속 매장을 확인해 등록 페이지를 '키오스크 모드'로 연다. 고객이 직접 입력한다. 가입매장은 자동 지정하고 담당 직원은 비워 둔다(직원이 CUS-04로 지정). 제출하면 입력값을 지우고 첫 화면으로 돌아간다. 이 모드에서는 다른 메뉴와 고객 정보에 접근할 수 없다 | MVP (줄이는 순서 1단계) |
| REG-03 | QR 등록 | 고객이 본인 폰으로 매장 QR을 찍어 같은 폼을 입력한다. QR에 매장 코드(선택: 직원 코드)를 담아 가입매장·담당 직원을 자동 지정. 직원 코드가 없거나, 없는 코드거나, 비활성·다른 매장 직원이면 등록은 받고 담당 직원만 비운다(직원이 CUS-04로 지정). QR 이미지는 본사가 매장 상세에서 받는다(ADM-01·03). 로그인 없는 공개 페이지라 요청 수를 제한한다 (NFR-04a) | MVP (줄이는 순서 1단계) |
| REG-04 | 직원 대리 등록 | 직원이 매장 계정에서 같은 폼을 열어 입력한다. 판매 기록 중 검색 결과가 없으면 그 자리에서 등록하고 판매로 돌아온다 | MVP |
| REG-05 | 중복 확인 | 같은 전화번호가 있으면 새로 만들지 않는다 (BR-01). 고객용 화면(iPad, QR)에서는 기존 가입 여부를 드러내지 않고 같은 완료 메시지를 보여주며, 기존 정보도 덮어쓰지 않는다 (남의 번호로 정보를 바꾸는 것을 막기 위해). 직원 화면에서는 기존 고객을 보여준다 | MVP |
| REG-06 | 외국인 입력 | 외국인 선택 시 국가번호 포함 전화번호, 영문 이름(필수). 한글 이름은 선택이고, 비우면 영문 이름을 이름 칸에도 넣어 고객명 검색(CUS-01)에 걸리게 한다 | MVP |

| GRD-05 | 정기 산정 | 매년 6월 1일 새벽, 전체 고객을 막 끝난 시즌(작년 6월 1일 ~ 올해 5월 31일) 실적으로 다시 산정해 다음 시즌 등급을 정한다 (예: 25/26 시즌 실적 → 26/27 시즌 등급). 6월 한 달은 **임시**이고 7월 1일부터 **확정**이다. 강등은 이때만 일어난다. 6월 중 서버가 켜질 때도 한 번 실행하고, 몇 번 돌아도 결과가 같다 (BR-05, ADR-021). 패션 시즌 연도(24/25, 25/26)에 맞춘다. 데모에서는 수동 실행으로 보여준다 | MVP |
| GRD-06 | 등급 이력 | 모든 등급 변경을 이전 등급, 새 등급, 사유(즉시 승급 / 정기 산정 / 임시 등급 재계산 / 승급 취소), 그때의 시즌·티켓 수·순구매금액·합계 점수, 시각과 함께 기록 | MVP |
| MEM-01 | 상담 메모 작성 | 내용(최대 1,000자), 유형(상담/구매/연락/기타). 매장 계정에서 쓰면 작성 직원을 고른다 | MVP |

## 4. 비즈니스 규칙

**BR-01 고객 식별**

- 식별 키는 시스템이 발급하는 고객번호(`customer_id`)다. 이름과 전화번호는 식별 키가 아니다.
- 직원은 고객명으로 검색하고 목록에서 한 명을 선택한다. 같은 이름이 여럿이면 목록의 번호 뒷자리 4개를 고객에게 물어 확인한다. 매장 직원은 이름은 기억하지만 번호까지 기억하기는 어렵기 때문이다.
- 전화번호는 국제 표준 형식(E.164)으로 정규화해 저장한다 (`010-1234-5678` → `+821012345678`).
- 전화번호는 **중복 등록 방지**에 쓴다. 같은 번호는 한 고객만 가진다.
- **가족은 대표 1명**으로 등록하고, 가족의 구매는 모두 대표 고객으로 판매한다. 구성원은 고객이 아니라 대표 고객 아래 기록으로 둔다 (CUS-05, BR-13).

**BR-02 티켓 (구매 건 기준)**

- 티켓은 **구매 건**마다 1개다. 구매 건 = 판매 1건, 또는 추가 결제가 있는 교환 1건 (BR-17, ADR-022).
- 구매 건에서 받은 상품이 하나라도 남아 있으면 티켓이 살아 있다. 반품·교환·기록 취소로 모두 나가면 티켓에서 빠진다. 일부 반품은 금액과 수량에서만 뺀다.
- 기록 취소된 판매는 처음부터 없던 구매 건으로 본다 (BR-16).

**BR-03 산정 기간: 시즌**

- 실적은 **시즌** 단위로 센다. 시즌은 6월 1일 0시(한국 시간)부터 다음 해 6월 1일 0시 전까지다. 예: 26/27 시즌 = 2026-06-01 00:00 ~ 2027-05-31.
- 정기 산정은 막 끝난 시즌의 실적으로 다음 시즌 등급을 정한다 (25/26 시즌 실적 → 26/27 시즌 등급). 즉시 승급은 이번 시즌 누적 실적(시즌 시작 ~ 지금)으로 계산한다.
- 반품은 원래 판매한 날짜가 속한 시즌의 실적에서 뺀다. 지난 시즌 판매를 반품하면 이번 시즌 실적은 그대로이고, 6월(임시 기간)이면 지난 시즌 실적을 다시 계산해 임시 등급을 고친다 (BR-05).
- 지난 시즌 구매도 '누적 금액'에는 포함한다.
- 추가 결제 교환은 교환한 날, 추가 결제 없는 교환과 정정은 원래 판매 날짜의 시즌으로 센다 (BR-16·17).
- 시즌 시작일(6월 1일)과 길이(12개월)는 화면에서 바꾸지 않는다. 등급 계산기는 기간(시작·끝)을 받아 계산하므로, 엑셀 툴 비교 테스트(NFR-10)에는 36개월 기간을 넣는다.

**BR-04 점수와 등급**

- 금액 구간, 티켓 구간, 점수, 등급 컷은 **본사(HQ)가 정한다.** 시스템이 정답 값을 갖지 않는다.
- 기준은 브랜드 공통 1개다. 고객이 여러 매장에서 사도 등급이 하나여야 하기 때문이다.
- 아래는 **데모용 초기값**이다. 기존 엑셀 툴(36개월 기준)의 금액 구간을 시즌(12개월)에 맞게 3분의 1로 단순 환산한 값이라, 실제 운영 값이 아니다.

| 시즌 순구매금액 | 금액 점수 | 시즌 티켓 수 | 티켓 점수 |
| --- | --- | --- | --- |
| 100만원 미만 | 0 | 0건 | 0 |
| 100만원 이상 | 10 | 1건 | 10 |
| 200만원 이상 | 20 | 2건 | 20 |
| 300만원 이상 | 40 | 3건 | 30 |
| 400만원 이상 | 60 | 4건 이상 | 40 |

| 합계 점수 | 0~19 | 20~39 | 40~69 | 70~99 | 100 |
| --- | --- | --- | --- | --- | --- |
| 등급 | 일반 | D | C | B | A |
| 등급 코드 | `NORMAL` | `D` | `C` | `B` | `A` |

경계는 모두 "이상(>=)"으로 통일하고 단위 테스트로 고정한다.

- 등급 코드는 영문 대문자로 저장하고 주고받는다. "일반" 같은 한글은 화면 표시명이다.
- 등급 코드는 `NORMAL`, `D`, `C`, `B`, `A` 5개로 고정한다. 본사는 컷 점수와 할인율만 바꾸고, 등급을 더하거나 빼지 않는다.
- 화면에서 등급의 이름은 **"매장 단골 등급"** 이다. 이 서비스에 기록된 구매로만 계산하므로 브랜드 공식 멤버십 등급과 다를 수 있고, 둘이 헷갈리지 않게 이름을 구분한다.
- 등급의 높고 낮음은 등급 컷 점수로 정한다. 컷 점수가 높은 등급이 높은 등급이다. 콜리스트의 '최소 등급'과 BR-05의 등급 비교가 이 순서를 쓴다.

**BR-05 등급 부여: 승급은 즉시, 강등은 정기 산정 때만**

- **즉시 승급**: 판매완료 이벤트를 받으면 해당 고객의 이번 시즌 누적 실적에 더한다. 산정 등급이 현재 등급보다 높으면 바로 올린다.
- **정기 산정 (6월 1일)**: 전체 고객을 막 끝난 시즌 실적으로 다시 산정해 다음 시즌 등급을 정하고, 실적 집계는 새 시즌 기준으로 다시 시작한다. 실적이 줄어 등급이 내려가는 것은 이때만, 1년에 한 번 일어난다.
- **임시와 확정**: 6월 1일 ~ 6월 30일은 **임시** 기간이다. 이 기간에 지난 시즌 판매가 반품·교환·정정되면 지난 시즌 실적을 다시 계산해 임시 등급을 고친다(내려갈 수 있다). 7월 1일부터 **확정**이고, 이후 지난 시즌 판매가 반품돼도 확정 등급은 바뀌지 않는다. 6월 1일 직전에 사서 등급을 받고 그 뒤에 환불하는 것을 막기 위해서다. 브랜드 매장은 한 달쯤 지나면 환불을 거의 받지 않는다 (ADR-021).
- **적용 중 등급 = 임시·확정 등급과 이번 시즌 실적 기준 등급 중 높은 것.** 정기 산정도 이 식으로 정하므로, 6월 안에서는 정기 산정이 늦게 돌거나 여러 번 돌아도 결과가 같고 그 사이의 즉시 승급이 지워지지 않는다.
- **반품으로 승급 취소**: 반품·교환·기록 취소로 실적이 줄면 바로 다시 계산해, 적용 중인 등급을 실적 기준 등급까지 내린다. 단, 임시·확정 등급 아래로는 내려가지 않는다 (02-erd.md 3.4). 그래서 반품으로 취소되는 것은 지난 정기 산정 이후의 즉시 승급뿐이다. 구매 후 반품을 반복해 등급만 올리는 것을 막기 위해서다.
- **기준 변경**: 등급 컷·점수 구간을 바꾸면 **다음 6월 1일 정기 산정부터** 적용한다. 시즌 중에는 지금 기준을 유지하고 다시 계산하지 않는다. 6월(임시 기간)에 바꾸면 바로 적용하고 정기 산정을 다시 실행한다. 등급별 할인율은 등급에 영향이 없어 바로 적용한다 (ADR-027). 새 시즌 기준은 5월 안에 저장해 두도록 안내한다.
- **매일 다시 계산하지 않는다**: 시즌 누적은 판매·반품 때만 바뀌고 시간이 지나 빠지는 구매가 없으므로, 매일 새벽 실적 갱신은 하지 않는다 (ADR-020).
- 모든 등급 변경은 등급 이력에 사유와 그때의 점수를 함께 남긴다 (GRD-06).

**BR-06 판매 → 고객관리 이벤트 처리**

- 판매 저장과 같은 트랜잭션에서 이벤트를 `outbox` 테이블에 기록한다. 판매는 저장됐는데 이벤트가 사라지는 일을 막기 위해서다.
- 발행기가 outbox를 주기적으로 읽어 고객관리 모듈에 전달한다.
- 고객관리는 처리한 이벤트 ID를 기록해, **같은 이벤트가 두 번 와도 결과가 한 번 처리한 것과 같게** 한다 (멱등).
- 고객관리 처리가 실패해도 판매는 취소되지 않는다. 실패한 이벤트는 재시도 대상으로 남는다.
- **같은 판매의 이벤트는 발생 순서대로** 처리한다. 앞 이벤트(판매완료)가 처리되지 않았으면 뒤 이벤트(반품)는 기다린다. 반품이 없는 구매 기록을 고치는 일을 막기 위해서다.
- 재시도는 최대 10회. 그래도 실패하면 `FAILED`로 두고 로그를 남긴다. 원인을 고친 뒤 `PENDING`으로 되돌려 다시 처리한다 (MVP는 수동). 발행기는 1초마다 읽는다 (NFR-02).

**BR-07 비회원 판매**

- 고객을 지정하지 않은 판매도 저장한다. 고객관리에는 반영하지 않는다.
- 비회원 판매에는 등급 할인 안내가 없다. 판매 화면에서 "고객등록하면 등급 할인을 받을 수 있다"고 안내하고, 등록 후 같은 판매로 돌아온다 (REG-04).

**BR-08 동의와 수신**

- 개인정보 수집·이용 동의와 만 14세 이상 확인이 없으면 등록할 수 없다.
- 마케팅 수신은 문자·카톡 채널별로 동의 시각을 저장하고, 철회하면 비운다.
- 문자·카톡 중 하나라도 동의하면 "홍보 연락 가능"이다. 둘 다 미동의한 고객은 콜리스트에서 "홍보 연락 불가"로 표시한다.
- 할인 행사·신상 입고 같은 매장 공지는 광고성 정보다. 홍보 연락 가능한 고객에게만 보내고, 문자 앞에 "(광고)"를 붙이며, 밤 9시 ~ 아침 8시에는 보내지 않고, 수신 거부 방법을 안내한다 (운영 안내, 법률 검토 전).
- 상세주소를 받으므로 동의 문구에 수집 목적(예: 사은품·우편 발송)을 적고, 상세주소는 전화번호처럼 암호화해 저장한다. 고객 상세 화면에서도 기본으로 보여주지 않고 필요할 때만 따로 불러온다.
- 실제 운영 전에는 동의 문구와 보유기간을 개인정보보호 가이드로 확인해야 한다. 이 문서는 법률 검토를 거치지 않았다.

**BR-09 콜리스트 기본값**

- 직원 개인 계정: 담당 직원 = 본인, 등급 D 이상, 마지막 방문 후 90일 이상, 마지막 방문일이 오래된 순.
- 매장 계정: **이 매장 고객 전체 + 홍보 연락 가능만**. 이 매장 고객 = 이 매장에서 가입했거나 이 매장에서 산 적이 있는 고객, 그리고 매장 계정이 맡은 고객. 할인 행사·신상 입고 같은 매장 공지 대상을 뽑는 용도라 등급·방문 조건은 걸지 않는다.
- 본사: 매장을 골라서 본다.
- '최소 등급'은 적용 중 등급(`current`) 기준이다.
- 방문일은 구매일이다. 구매 없이 다녀간 방문은 기록하지 않는다.
- 구매가 없는 고객은 마지막 방문일이 비어 있다. '마지막 방문 후 N일' 조건과 정렬에서는 가입일로 계산한다. 가입만 하고 사지 않은 고객도 연락 대상이 되게 하기 위해서다.

**BR-10 결제 금액과 등급 할인 안내 (쿠폰 없음)**

- 판매 라인마다 **실제 결제 금액**을 기록한다. 결제는 매장의 ERP·POS·카드 단말기에서 이미 끝났고, 이 서비스는 그 결과를 고객 기록으로 남긴다 (ADR-014).
- 등록 상품을 고르면 화면이 "정가 × 수량 × (1 − 고객 등급 할인율)"(원 미만 버림)을 결제 금액 기본값으로 채운다. 직원은 실제 결제한 금액으로 고칠 수 있다. 직접 입력한 상품은 직원이 결제 금액을 적는다. 결제 금액은 0원 이상이다.
- 등급 할인율은 **안내**다. 판매 화면에 "B등급 · 할인 3% 대상"처럼 보여주고, 실제 할인은 결제하는 시스템에서 적용한다. 이 서비스가 결제를 막을 수 없으므로 직원 수동 할인 상한은 두지 않는다.
- 비회원 판매에는 등급 할인 안내가 없다 (BR-07).
- 등급 할인율은 본사(HQ)가 정하고 바로 적용된다 (ADR-027). 데모용 초기값: A 5% · B 3% · C 2% · D 1% · 일반 0%.
- 할인 안내는 판매 **전** 등급 기준이다. 이번 판매로 승급해도 이번 판매의 기본값에는 적용하지 않는다.
- 등록 상품 라인은 정가를 함께 남겨, 영수증 상세에서 정가와 결제 금액을 비교해 볼 수 있다.
- 등급 산정 금액은 결제 금액이다.

**BR-11 반품 환불 금액**

- 환불 금액 = 그 라인의 결제 금액 ÷ 판매 수량 × 반품 수량, 원 미만 버림.
- 그 라인의 마지막 남은 수량을 반품할 때는 남은 결제 금액을 전부 환불한다. 여러 번 나눠 반품해도 환불 합계가 결제 금액과 같아야 하기 때문이다 (예: 3개 100원 → 33원, 33원, 34원).

**BR-12 판매·반품 중복 저장 방지**

- 판매등록 화면과 반품 창은 열 때 요청 키(UUID)를 하나 만들어 저장 요청에 붙인다.
- 같은 키로 다시 오면 새로 저장하지 않고 처음 저장한 결과를 그대로 돌려준다. 버튼을 두 번 누르거나 네트워크가 다시 보내도 판매·반품은 한 건이다. 반품이 두 번 저장되면 "1개 반품"이 2개가 되므로 반품에도 같은 규칙을 쓴다.
- 같은 키로 다른 내용이 오면 거절한다. 저장이 끝나면 화면은 다음 판매·반품을 위해 새 키를 만든다.
- 저장 위치와 방식은 ADR-006, 03-api.md 4.1·4.2.
- 교환·정정·기록 취소도 같은 규칙을 쓴다 (03-api.md 4.8·4.9).

**BR-13 가족 구성원**

- 구성원은 고객이 아니다. 전화번호·동의·등급·로그인이 없고, 대표 고객 아래 기록이다.
- 판매·등급·구매이력은 대표 고객 하나에 쌓인다. 그래서 가족 실적은 따로 합산 규칙 없이 대표 고객의 실적이 된다.
- 이름은 실명 대신 호칭으로 받는다. CRM에는 아이 이름이 필요 없고, 만 14세 미만의 개인정보는 법정대리인 동의 등 따질 것이 많기 때문이다. 동의 문구의 수집 항목에 가족 구성원 정보(호칭, 관계, 사이즈)를 적는다 (BR-08).
- 사이즈 목록은 구성원 성별로 정한다(고객과 같은 규칙, REG-01). 자녀는 아동 의류 사이즈(4·6·8·10)도 고를 수 있다. 아동 신발은 다루지 않는다 (02-erd.md 3.2).
- 착용자: 판매 라인마다 구성원을 고를 수 있다(선택). 판매 기록에는 호칭을 복사해 두어, 구성원을 지우거나 호칭을 바꿔도 과거 영수증은 그대로다. 비회원 판매에는 고를 수 없다.
- 콜리스트 가족 필터: 고른 관계의 구성원이 있는 고객만 보여준다 (예: 자녀가 있는 고객).

**BR-14 후속 연락 (2일·2주·2달)**

- 회원 구매가 고객 모듈에 반영될 때(판매 이벤트 처리) 할 일을 만든다. 비회원 판매는 만들지 않는다.
- 기본 단계는 3개다. 판매일 기준 **2일 뒤 "감사 인사"**, **2주 뒤 "착용감 확인"**, **2달 뒤 "신상·재방문 안내"**. 2달은 달력 기준(예: 10월 15일 → 12월 15일)이다.
- 할 일은 고객의 담당 직원에게 간다. 담당 직원이 없거나 비활성이면 판매 화면에서 고른 판매 사원이 받는다. 매장 계정이 맡은 고객의 할 일은 매장 계정이 받아, 매장 노트북·매장폰의 오늘 할 일에 "매장 할 일"로 나온다.
- "오늘 할 일"에는 만기일이 오늘이거나 지난, 아직 끝나지 않은 할 일이 만기일이 오래된 순으로 나온다.
- 할 일에서 연락 결과(통화 완료·부재·재연락)를 기록하면 완료된다. 기록 없이 끝낼 때는 "건너뛰기"를 누른다.
- 그 판매가 전부 반품되거나 기록 취소되면 남은 할 일은 자동으로 취소한다. 교환은 새 할 일을 만들지 않고 원 판매의 할 일을 그대로 둔다. 정정은 원래 판매 시각으로 할 일을 다시 만든다.
- 같은 고객이 또 사면, 이전 구매에서 아직 끝나지 않은 할 일은 닫고 새 구매 기준으로 다시 만든다. 연락이 겹치지 않게 하기 위해서다.
- 단계마다 "홍보 연락" 여부를 둔다(기본: 2달 단계만 홍보). 홍보 단계는 문자·카톡 수신에 동의하지 않은 고객에게 "홍보 연락 불가"로 표시하고, 홍보 없는 안부 연락만 안내한다 (BR-08).
- 설정은 본사(HQ)가 바꾼다. 바꾼 설정은 이후 구매부터 적용되고, 이미 만든 할 일은 그대로다.

**BR-15 직급과 이관**

- 직급 순서: 매장 계정 > 매니저 > 시니어 > 주니어 > 스태프. 매니저는 매장마다 메인 1명 + 임시 1명까지다 (넘으면 등록 거절).
- 직원을 비활성화하면 그 직원의 담당 고객과 열린 후속 연락 할 일을 한 번에 넘긴다. 넘겨받을 수 있는 사람은 **같은 직급 이상**이다.

| 퇴사자 | 넘겨받을 수 있는 사람 |
| --- | --- |
| 메인 매니저 | 매장 계정 (임시 매니저가 인수인계 중에 그만둘 수 있으므로 항상 매장 계정) |
| 임시 매니저 | 메인 매니저 (없으면 매장 계정) |
| 시니어 | 매니저, 시니어 |
| 주니어 | 매니저, 시니어, 주니어 |
| 스태프 | 매니저, 시니어, 주니어, 스태프 |
| 받을 사람이 없을 때 | 매장 계정 |

- 매장 계정이 맡은 고객은 본사가 매장 안의 누구에게든 다시 넘길 수 있다. 임시 매니저를 메인으로 승격한 뒤 넘기는 것이 보통의 흐름이다.
- 비활성화할 때는 매장 계정 비밀번호도 새로 정한다. 공용 비밀번호를 아는 사람이 나가기 때문이다.
- 비활성화와 이관은 함께 성공하거나 함께 실패한다 (ADR-024). 넘긴 사람·받은 사람·고객 수·시각은 로그로 남긴다.

**BR-16 판매 잠금: 하루 마감과 정정**

- 판매한 날, 마감 전에는 매장 계정이 판매를 고치거나 기록 취소할 수 있다. 정정은 원 판매를 기록 취소하고 고친 내용으로 **원래 판매 시각**에 다시 기록한다. 새 영수증 번호를 받고 원 판매와 연결한다. 판매 사원은 원래 직원이고, 고친 계정은 따로 남긴다 (ADR-026).
- 기록 취소된 판매는 없던 구매로 본다. 티켓·실적에서 빠지고 남은 할 일은 취소된다. 판매 내역에는 "기록 취소"로 남는다.
- 매장 계정에서 "오늘 판매 마감"을 누르면 그날 판매가 잠긴다. 누르지 않으면 자정에 자동으로 잠긴다. 잠긴 날에는 판매·반품·교환을 새로 기록할 수 없다. 다시 여는 것은 본사다.
- 잠긴 판매를 고칠 때는 본사에 요청하고(시스템 밖), 본사가 고친다. 이때만 지난 날짜로 다시 기록할 수 있다.
- 등급은 반품과 같은 규칙을 따른다. 7월 1일 이후 지난 시즌 판매를 고치면 확정 등급은 바뀌지 않는다 (BR-05).

**BR-17 교환**

- 교환은 원 판매의 라인 일부를 반품하고 새 상품을 한 번에 기록하는 것이다. 추가 결제와 차액 환불 모두 그대로 기록한다.
- **추가 결제가 있으면** 교환이 새 구매 건이 되어 티켓이 1개 늘고, 교환한 날의 시즌으로 센다. 단, 원 판매 1건에서 교환으로 생기는 티켓은 최대 1개다.
- **추가 결제가 없으면**(같은 금액이거나 차액 환불) 새 상품은 원래 구매 건에 붙는다. 티켓은 그대로이고 원래 판매 날짜의 시즌으로 센다.
- 교환으로 원래 구매 건의 상품이 모두 나가면 그 구매 건의 티켓이 빠진다 (BR-02). 예: 1·2·3을 사고 1을 환불, 2를 4·5로 추가 결제 교환, 3을 환불하면 티켓은 4·5가 남은 교환 1건뿐이다.
- 교환은 새 후속 연락 할 일을 만들지 않는다 (BR-14).

## 10. 리스크

- **범위 확장**: 새 아이디어는 먼저 '다음'이나 '나중' 칸에 적고, MVP가 끝난 뒤 판단한다.
- **시간**: 2026-10-23 기준 남은 작업은 약 141시간이고, 주 20시간으로 12/09까지 맞춘다 (project-plan 6장). 11/04 점검에서 계획보다 20% 넘게 느리면 아래 순서로 줄인다. 1단계 항목은 7주 차에 몰아 두어 빼기 쉽게 했다.
  - **1단계** (다음 단계로 미루거나 Swagger·기본값으로 대체)
    1. 키오스크·QR 등록 (REG-02·03) → 고객 등록은 매장 계정에서 직원이 대리 입력
    2. 상품 엑셀 (PRD-02) → 화면에서 한 개씩 등록
    3. 설정·관리 화면 (등급 기준, 후속 연락 설정, 본사 직원 관리) → Swagger와 시드 데이터
    4. 판매 정정 (SAL-07의 정정) → 기록 취소 + 다시 기록만
    5. 메인/임시 매니저 구분 → 매니저 1명, 퇴사하면 매장 계정을 거쳐 이관
    6. 판매 시 착용자 선택 (CUS-05 일부) → 구성원 관리와 가족 필터는 남김
    7. 직원 알림함 (CAL-09) → 오늘 할 일 화면으로 대신
  - **2단계** (1단계로도 모자랄 때)
    1. 교환 (SAL-06) → 반품 + 새 판매 (티켓이 틀어질 수 있음을 문서에 남김)
    2. 가족 구성원 (CUS-05)
    3. 개인정보 암호화 (NFR-04) → 평문 저장 + 화면 가리기
- **무료 서버의 잠자기**: 요청이 없으면 잠드는 무료 서버는 6월 1일 새벽 정기 산정을 놓칠 수 있다. 6월 중 서버가 켜질 때 한 번 더 실행하고, 정기 산정은 몇 번 돌아도 결과가 같으므로(BR-05) 실행 기록을 따로 두지 않는다.
- **공용 매장 계정**: 매장 직원 모두가 매장 계정 비밀번호를 안다. 직원이 퇴사하면 본사가 매장 계정 비밀번호를 새로 정하고(BR-15), 바꾸면 기존 로그인이 모두 끊긴다 (AUTH-04).
- **암호화와 검색**: 전화번호를 암호화하면 번호 부분 검색이 안 된다. 검색은 고객명으로만 하고 목록의 뒷자리로 확인한다 (CUS-01).
- **공개 등록 페이지 악용**: QR 페이지는 로그인이 없어 허위 등록이 가능하다. MVP는 요청 수 제한으로 막고, SMS 인증은 다음 단계에서 더한다.

> 변경: 2026-10-16 11장 확인 필요의 답 반영 — 정기 산정을 매년 6월 1일로(GRD-05, BR-05), 기간 구매 포함/제외 필터는 다음(CAL-05), 서비스 이름 CRM pos, 배포는 무료 배포.

## 1. 범위 요약

- 단일 브랜드, 여러 매장. 웹사이트 1개, 서버 1개, DB 1개 (모듈러 모놀리스).
- 모듈 구성

| 모듈 | 메뉴 | 역할 |
| --- | --- | --- |
| `sales` | 매장 업무 › 판매등록, 판매 내역 | 판매·반품 등록, 판매 이벤트 발행 |
| `customer` | 매장 업무 › 고객등록 / 고객관리 전체 | 고객, 가족 구성원, 구매이력, 등급, 상담 메모, 콜리스트 |
| `product` | (화면 없음) | 상품 마스터 조회. 더미 데이터로 채운다 |
| `common` | 로그인, 관리 | 인증, 직원, 매장 |

- 범위 밖: 재고(나중), 결제 연동(나중), POS·ERP 연동(나중).

## 2. 사용자와 권한

| 역할 | 누구 | 할 수 있는 일 |
| --- | --- | --- |
| STAFF | 매장 판매직원, 매장 매니저 | 판매·반품 등록, 고객 등록·조회·수정(가족 구성원 포함), 메모, 콜리스트, 상품 조회, 등급 기준 조회 |
| MANAGER | 본사 CRM 담당 | STAFF 전부(판매 등록 제외, 아래 참고) + 등급 기준 관리, 전 매장 직원·키오스크 계정 관리, 전체 재계산 |
| KIOSK | 매장 iPad 계정 (매장별, MANAGER가 만든다) | 고객 등록 폼만 (REG-02). 호출할 수 있는 API는 등록, 내 정보 조회(`GET /me`), 공개 API뿐 |

- 고객은 로그인 없이 등록 폼만 쓴다 (매장 iPad 또는 QR, REG-02·03).
- 등급 기준은 브랜드 공통이므로 바꾸는 권한은 본사(MANAGER)에만 둔다. 매장 매니저 전용 권한(자기 매장 직원만 관리)은 다음 단계.
- **판매 매장은 로그인한 계정의 소속 매장이다.** 요청으로 매장을 받지 않는다. 본사 계정은 소속 매장이 없으므로 판매를 등록할 수 없다 (03-api.md `STORE_REQUIRED`).
- 조회 범위: 고객은 여러 매장에서 사므로 STAFF도 브랜드 전체 고객을 조회한다. 판매 내역은 기본값이 자기 매장이고 다른 매장을 골라 볼 수 있다. 본사 계정은 매장을 골라서 본다.

## 3. 기능 요구사항

### 3.1 매장 업무: 판매 (SAL)

| ID | 기능 | 상세 | 단계 |
| --- | --- | --- | --- |
| SAL-01 | 판매등록 | 고객 선택(생략 가능, BR-07) → 품번·품명으로 상품 검색 → 색상·사이즈·수량 → 착용자(가족 구성원, 선택, BR-13) → 실판매가(MVP는 정가 고정, BR-10) → 할인율(회원은 등급 할인 자동, 직원 수정 가능, BR-10) → 저장. 판매 매장은 로그인한 계정의 소속 매장(2장). 영수증 번호 자동 발급(`매장코드-판매일자-순번`, 예: GN01-20261015-0012). 저장 버튼을 두 번 눌러도 판매는 한 건만 생긴다 (BR-12) | MVP |
| SAL-02 | 판매완료 이벤트 | 판매 저장과 같은 트랜잭션에서 이벤트를 기록하고, 고객관리 모듈에 전달한다 (BR-06) | MVP |
| SAL-03 | 반품 | 원 판매를 지정해 라인 단위로 반품 → 반품 이벤트 발행. 남은 수량보다 많이 반품할 수 없다. 환불 금액은 BR-11, 중복 저장 방지는 BR-12 | MVP |
| SAL-04 | 응대 메모 | 판매등록 화면에서 메모를 쓰면 판매와 함께 저장되고 고객의 상담 메모(유형 '구매')에 남는다. 비회원 판매에는 메모 입력란을 보이지 않는다 | MVP |
| SAL-05 | 판매 내역 | 매장·기간별 판매 목록(기본은 내 매장, 2장), 영수증 상세(라인, 할인, 반품 내역) | MVP |

### 3.2 매장 업무: 고객등록 (REG)

종이 고객등록카드를 대신한다. **같은 등록 폼**을 세 곳에서 연다: 매장 iPad, 고객 본인 폰(QR), 직원 화면.

| ID | 기능 | 상세 | 단계 |
| --- | --- | --- | --- |
| REG-01 | 고객 등록 폼 | 필수: 이름(외국인은 영문 이름, REG-06), 전화번호, 내/외국인(`DOMESTIC`·`FOREIGN`, 기본 내국인), 개인정보 수집·이용 동의, 만 14세 이상 확인. 선택: 생년, 생일(월일), 주소(시/도, 구, **상세주소**), 성별(`F` 여성·`M` 남성), 선호 품목(복수 선택), 사이즈(상의/아우터/하의/신발, 허용값은 02-erd.md 3.2), 연락 채널(`CALL` 전화·`SMS` 문자·`KAKAO` 카톡), 마케팅 수신(문자/카톡 각각). 아우터·하의 사이즈 목록은 성별로 나뉘므로, 성별을 고르지 않으면 아우터·하의 사이즈 칸을 숨긴다 | MVP |
| REG-02 | 매장 iPad 등록 | 본사가 매장별로 만든 키오스크 계정(KIOSK)으로 iPad에서 로그인하면, 내 정보(`GET /me`)로 역할과 소속 매장을 확인해 등록 페이지를 '키오스크 모드'로 연다. 고객이 직접 입력한다. 가입매장은 자동 지정하고 담당 직원은 비워 둔다(직원이 CUS-04로 지정). 제출하면 입력값을 지우고 첫 화면으로 돌아간다. 이 모드에서는 다른 메뉴와 고객 정보에 접근할 수 없다 | MVP |
| REG-03 | QR 등록 | 고객이 본인 폰으로 매장 QR을 찍어 같은 폼을 입력한다. QR에 매장 코드(선택: 직원 코드)를 담아 가입매장·담당 직원을 자동 지정. 직원 코드가 없거나, 없는 코드거나, 비활성·다른 매장 직원이면 등록은 받고 담당 직원만 비운다(직원이 CUS-04로 지정). QR 이미지는 본사가 직원 관리 화면에서 받는다(ADM-01). 로그인 없는 공개 페이지라 요청 수를 제한한다 (NFR-04a) | MVP |
| REG-04 | 직원 대리 등록 | 직원이 같은 폼을 열어 입력. 판매등록 중 검색 결과가 없으면 그 자리에서 등록하고 판매로 돌아온다 | MVP |
| REG-05 | 중복 확인 | 같은 전화번호가 있으면 새로 만들지 않는다 (BR-01). 고객용 화면(iPad, QR)에서는 기존 가입 여부를 드러내지 않고 같은 완료 메시지를 보여주며, 기존 정보도 덮어쓰지 않는다 (남의 번호로 정보를 바꾸는 것을 막기 위해). 직원 화면에서는 기존 고객을 보여준다 | MVP |
| REG-06 | 외국인 입력 | 외국인 선택 시 국가번호 포함 전화번호, 영문 이름(필수). 한글 이름은 선택이고, 비우면 영문 이름을 이름 칸에도 넣어 고객명 검색(CUS-01)에 걸리게 한다 | MVP |
| REG-07 | SMS 본인 인증 | 고객용 화면에서 전화번호를 입력하면 인증번호 6자리를 문자로 보내고, 입력해야 등록이 끝난다. 남의 번호나 오타 번호로 등록되는 것을 막는다. 문자 발송 비용이 들어 MVP에서는 빼고, 발송 부분만 갈아끼울 수 있게 설계해 둔다 | 다음 |

### 3.3 고객관리 (CUS · GRD · MEM · CAL)

| ID | 기능 | 상세 | 단계 |
| --- | --- | --- | --- |
| CUS-01 | 고객 검색 | 고객명으로 검색(부분 일치) → 목록에서 선택. 목록: 이름, 마스킹 번호(뒷자리), 등급, 마지막 방문일, 담당 직원. 필요하면 번호 뒷자리로 좁힌다 | MVP |
| CUS-02 | 고객 상세 요약 | 등급·점수·등급 할인율, 가입매장·가입일, 담당 직원, 첫/마지막 방문일(BR-09), 최근 12개월 티켓 수·구매 수량·순구매금액, 누적 금액. 상세주소는 기본으로 보여주지 않고 필요할 때만 따로 불러온다 (BR-08) | MVP |
| CUS-03 | 구매이력 | 영수증별로 묶어 상품·색상·사이즈·금액·착용자, 반품 표시. 최신순, 페이지 단위 | MVP |
| CUS-04 | 프로필 수정 | 선택 항목, 담당 직원, 마케팅 수신 변경. 이름과 전화번호도 고칠 수 있다. 바꾼 번호가 다른 고객에게 이미 있으면 바꾸지 않고 그 고객을 알려준다 (BR-01, REG-05와 같은 규칙) | MVP |
| CUS-05 | 가족 구성원 | 대표 고객 아래 구성원을 추가·수정·삭제한다. 호칭(실명 대신, 예: 첫째 딸), 관계(배우자/자녀/부모/기타), 성별·출생연도·사이즈(선택). 직원 화면(고객 상세)에서만 관리하고 고객 등록 폼(iPad, QR)에는 넣지 않는다. 판매 시 라인마다 착용자를 고를 수 있다 (BR-13) | MVP |
| CUS-06 | 고객 정보 삭제 | 고객이 요청하면 개인정보를 지운다. 판매 기록과 등급 집계를 어떻게 남길지는 그때 정한다 (BR-08의 법률 검토와 함께) | 다음 |
| GRD-01 | 등급 산정 | 최근 12개월 티켓 점수 + 금액 점수 = 합계 → 등급 (BR-03·04) | MVP |
| GRD-02 | 즉시 승급 | 판매완료 이벤트를 받으면 해당 고객의 실적을 다시 계산하고, 산정 등급이 현재 등급보다 높으면 바로 올린다. 낮아져도 바로 내리지 않는다 (BR-05) | MVP |
| GRD-03 | 점수 근거 표시 | "티켓 4건 40점 + 금액 ○○만원 ○○점"과 함께 '현재 등급'과 '현재 실적 기준 등급'을 같이 보여준다 (예: 현재 A, 실적 기준 B → 다음 정기 산정 때 B). 실적은 매일 새벽 다시 계산한다 (BR-05) | MVP |
| GRD-04 | 등급 기준 관리 | 금액·티켓 구간, 점수, 등급 컷, 등급별 할인율, 직원 수동 할인 상한 수정. 브랜드 공통 기준 1개. 수정하면 새 버전. 등급 할인율이 수동 할인 상한보다 크면 저장하지 않는다 (BR-10). 등급 코드와 산정 기간은 화면에서 바꾸지 않는다 (BR-03·04) | MVP |
| GRD-05 | 정기 산정 | 매년 6월 1일 새벽, 전체 고객을 직전 12개월(작년 6월 1일 ~ 올해 5월 31일) 실적으로 다시 산정해 등급을 확정한다. 이때만 강등된다. 패션 시즌 연도(24/25, 25/26)에 맞춘다. 데모에서는 수동 실행으로 보여준다 | MVP |
| GRD-06 | 등급 이력 | 모든 등급 변경을 이전 등급, 새 등급, 사유(즉시 승급 / 정기 산정 / 반품으로 승급 취소 / 기준 변경), 시각과 함께 기록 | MVP |
| MEM-01 | 상담 메모 작성 | 내용(최대 1,000자), 유형(상담/구매/연락/기타) | MVP |
| MEM-02 | 메모 목록 | 최신순, 작성자·작성일 | MVP |
| MEM-03 | 메모 수정·삭제 | 본인 메모만, MANAGER는 전체 | MVP |
| CAL-01 | 콜리스트 | 필터 조합: 담당 직원(기본 = 나), 최소 등급, 마지막 방문 후 N일(BR-09), 구매 대상(여성/남성/아동/공용)·품목(아우터/상의/하의/신발/액세서리), 가족 구성원 관계(예: 자녀가 있는 고객, BR-13). 문자·카톡 둘 다 미동의한 고객은 "홍보 연락 불가" 표시 (BR-08) | MVP |
| CAL-02 | 연락 결과 기록 | 통화 완료 / 부재 / 재연락 + 메모 (메모 유형 '연락'으로 저장) | MVP |
| CAL-03 | 폰에서 바로 전화 | `tel:` 링크 | 다음 |
| CAL-04 | 생일 고객 | 이번 달 생일 고객 목록 | 다음 |
| CAL-05 | 기간 구매 필터 | 달력으로 기간을 골라, 그 기간에 (고른 상품군을) 산 고객을 포함하거나 제외한다. 예: 작년 10~12월에 아우터를 산 고객만 | 다음 |

### 3.5 관리 (AUTH · ADM)

| ID | 기능 | 상세 | 단계 |
| --- | --- | --- | --- |
| AUTH-01 | 로그인 | 아이디 + 비밀번호, JWT(Access 30분 + Refresh 14일). 로그인 후 내 정보(이름, 역할, 소속 매장)를 조회한다 | MVP |
| AUTH-02 | 역할 권한 | 등급 기준 관리, 직원 관리는 MANAGER(본사)만. 판매 등록은 소속 매장이 있는 계정만 (2장). 비활성화된 계정은 로그인을 거절하고, Refresh 토큰이 남아 있어도 재발급하지 않는다 | MVP |
| ADM-01 | 직원 관리 | 직원·키오스크 계정 등록(소속 매장, 역할), 비활성화. 매장 QR·직원 QR 이미지 내려받기 (REG-03) | MVP |

## 4. 비즈니스 규칙

**BR-01 고객 식별**

- 식별 키는 시스템이 발급하는 고객번호(`customer_id`)다. 이름과 전화번호는 식별 키가 아니다.
- 직원은 고객명으로 검색하고 목록에서 한 명을 선택한다. 매장 직원은 이름은 기억하지만 번호까지 기억하기는 어렵기 때문이다.
- 전화번호는 국제 표준 형식(E.164)으로 정규화해 저장한다 (`010-1234-5678` → `+821012345678`).
- 전화번호는 **중복 등록 방지**에 쓴다. 같은 번호는 한 고객만 가진다.
- **가족은 대표 1명**으로 등록하고, 가족의 구매는 모두 대표 고객으로 판매한다. 구성원은 고객이 아니라 대표 고객 아래 기록으로 둔다 (CUS-05, BR-13).

**BR-02 티켓**

- 티켓 1건 = 판매 1건(영수증 1장).
- 전부 반품된 판매는 티켓 수에서 제외한다. 일부 반품은 금액과 수량에서만 뺀다.

**BR-03 산정 기간**

- 산정 기준일로부터 **최근 12개월**. 기준일의 12개월 전 같은 날 0시부터(>=) 구매를 센다. 예: 2027-06-01 정기 산정이면 2026-06-01 00:00 이후 구매. 즉시 승급·일일 실적 갱신은 계산하는 날이 기준일이다.
- 반품은 원래 판매한 날짜의 실적에서 뺀다. 12개월 밖 판매를 반품하면 누적 금액에서만 빠진다.
- 12개월 밖 구매도 '누적 금액'에는 포함한다.
- 기간 길이는 등급 기준에 저장된 설정값이다(기본 12개월). 화면에서는 바꾸지 않고, 엑셀 툴 비교 테스트(NFR-10, 36개월)에서만 바꾼다.

**BR-04 점수와 등급**

- 금액 구간, 티켓 구간, 점수, 등급 컷은 **MANAGER(본사)가 정한다.** 시스템이 정답 값을 갖지 않는다.
- 기준은 브랜드 공통 1개다. 고객이 여러 매장에서 사도 등급이 하나여야 하기 때문이다.
- 아래는 **데모용 초기값**이다. 기존 엑셀 툴(36개월 기준)의 금액 구간을 12개월에 맞게 3분의 1로 단순 환산한 값이라, 실제 운영 값이 아니다.

| 최근 12개월 순구매금액 | 금액 점수 | 최근 12개월 티켓 수 | 티켓 점수 |
| --- | --- | --- | --- |
| 100만원 미만 | 0 | 0건 | 0 |
| 100만원 이상 | 10 | 1건 | 10 |
| 200만원 이상 | 20 | 2건 | 20 |
| 300만원 이상 | 40 | 3건 | 30 |
| 400만원 이상 | 60 | 4건 이상 | 40 |

| 합계 점수 | 0~19 | 20~39 | 40~69 | 70~99 | 100 |
| --- | --- | --- | --- | --- | --- |
| 등급 | 일반 | D | C | B | A |
| 등급 코드 | `NORMAL` | `D` | `C` | `B` | `A` |

경계는 모두 "이상(>=)"으로 통일하고 단위 테스트로 고정한다.

- 등급 코드는 영문 대문자로 저장하고 주고받는다. "일반" 같은 한글은 화면 표시명이다.
- 등급 코드는 `NORMAL`, `D`, `C`, `B`, `A` 5개로 고정한다. MANAGER는 컷 점수와 할인율만 바꾸고, 등급을 더하거나 빼지 않는다.
- 등급의 높고 낮음은 등급 컷 점수로 정한다. 컷 점수가 높은 등급이 높은 등급이다. 콜리스트의 '최소 등급'과 BR-05의 등급 비교가 이 순서를 쓴다.

**BR-05 등급 부여: 승급은 즉시, 강등은 정기 산정 때만**

- **즉시 승급**: 판매완료 이벤트를 받으면 해당 고객의 최근 12개월 실적을 다시 계산한다. 산정 등급이 현재 등급보다 높으면 바로 올린다.
- **강등은 정기 산정 때만**: 매년 6월 1일 새벽 전체 고객을 직전 12개월 실적으로 다시 산정해 등급을 확정한다. 실적이 줄어 등급이 내려가는 것은 이때만, 1년에 한 번 일어난다.
- **반품으로 승급 취소**: 반품으로 실적이 줄면 적용 중인 등급을 실적 기준 등급까지 내린다. 단, 마지막 정기 산정에서 확정된 등급 아래로는 내려가지 않는다 (반품 후 등급 = 실적 기준 등급과 확정 등급 중 높은 것, 02-erd.md 3.4). 그래서 반품으로 취소되는 것은 지난 정기 산정 이후의 즉시 승급뿐이다. 구매 후 반품을 반복해 등급만 올리는 것을 막기 위해서다.
- **기준 변경**: 기준을 바꾸면 전체 고객을 다시 계산하되 같은 규칙을 따른다. 오르는 고객은 바로 오르고, 내려가는 고객은 다음 정기 산정 때 내려간다.
- **일일 실적 갱신**: 매일 새벽 전체 고객의 최근 12개월 실적과 '실적 기준 등급'을 다시 계산한다. 시간이 지나 12개월 밖으로 빠진 구매를 반영하기 위해서다. 시간이 지나면 실적은 줄기만 하므로, 이 작업은 적용 중인 등급을 바꾸지 않는다. 몇 번 돌아도 결과가 같으므로 서버가 시작될 때도 한 번 실행한다 (10장).
- 모든 등급 변경은 등급 이력에 사유와 함께 남긴다 (GRD-06).

**BR-06 판매 → 고객관리 이벤트 처리**

- 판매 저장과 같은 트랜잭션에서 이벤트를 `outbox` 테이블에 기록한다. 판매는 저장됐는데 이벤트가 사라지는 일을 막기 위해서다.
- 발행기가 outbox를 주기적으로 읽어 고객관리 모듈에 전달한다.
- 고객관리는 처리한 이벤트 ID를 기록해, **같은 이벤트가 두 번 와도 결과가 한 번 처리한 것과 같게** 한다 (멱등).
- 고객관리 처리가 실패해도 판매는 취소되지 않는다. 실패한 이벤트는 재시도 대상으로 남는다.
- **같은 판매의 이벤트는 발생 순서대로** 처리한다. 앞 이벤트(판매완료)가 처리되지 않았으면 뒤 이벤트(반품)는 기다린다. 반품이 없는 구매 기록을 고치는 일을 막기 위해서다.
- 재시도는 최대 10회. 그래도 실패하면 `FAILED`로 두고 로그를 남긴다. 원인을 고친 뒤 `PENDING`으로 되돌려 다시 처리한다 (MVP는 수동). 발행기는 1초마다 읽는다 (NFR-02).

**BR-07 비회원 판매**

- 고객을 지정하지 않은 판매도 저장한다. 고객관리에는 반영하지 않는다.
- 비회원 판매는 할인을 받을 수 없다. 판매 화면에서 "고객등록하면 등급 할인을 받을 수 있다"고 안내하고, 등록 후 같은 판매로 돌아온다 (REG-04).

**BR-08 동의와 수신**

- 개인정보 수집·이용 동의와 만 14세 이상 확인이 없으면 등록할 수 없다.
- 마케팅 수신은 문자·카톡 채널별로 동의 시각을 저장하고, 철회하면 비운다.
- 문자·카톡 중 하나라도 동의하면 "홍보 연락 가능"이다. 둘 다 미동의한 고객은 콜리스트에서 "홍보 연락 불가"로 표시한다.
- 상세주소를 받으므로 동의 문구에 수집 목적(예: 사은품·우편 발송)을 적고, 상세주소는 전화번호처럼 암호화해 저장한다. 고객 상세 화면에서도 기본으로 보여주지 않고 필요할 때만 따로 불러온다.
- 실제 운영 전에는 동의 문구와 보유기간을 개인정보보호 가이드로 확인해야 한다. 이 문서는 법률 검토를 거치지 않았다.

**BR-09 콜리스트 기본값**

- 담당 직원 = 로그인한 본인, 등급 D 이상, 마지막 방문 후 90일 이상, 마지막 방문일이 오래된 순.
- 방문일은 구매일이다. 구매 없이 다녀간 방문은 기록하지 않는다.
- 구매가 없는 고객은 마지막 방문일이 비어 있다. '마지막 방문 후 N일' 조건과 정렬에서는 가입일로 계산한다. 가입만 하고 사지 않은 고객도 연락 대상이 되게 하기 위해서다.

**BR-10 할인 (쿠폰 없음)**

- MVP에서 실판매가는 정가로 고정한다. 직원이 단가를 내릴 수 있으면 할인 상한이 의미가 없어지기 때문이다. 세일가는 나중에 상품 마스터의 판매가로 다룬다.
- 할인은 판매 라인마다 정수 %로 적용한다. 할인 금액 = 실판매가 × 수량 × 할인율, 원 미만 버림.
- 회원 판매: 고객의 현재 등급 할인율이 자동으로 채워진다. 직원은 라인별로 바꿀 수 있지만 상한(기본 30%)을 넘을 수 없다. 바꾼 라인은 '수동 할인'으로 기록한다.
- 비회원 판매: 할인 0%, 수정 불가 (BR-07).
- 등급 할인율과 수동 할인 상한은 MANAGER가 정한다. 데모용 초기값: A 5% · B 3% · C 2% · D 1% · 일반 0%.
- 등급 할인율은 수동 할인 상한 이하여야 한다. 넘으면 자동으로 채운 할인이 상한에 걸려 회원 판매가 막히므로, 기준을 저장할 때 막는다 (GRD-04).
- 할인은 판매 **전** 등급 기준이다. 이번 판매로 승급해도 이번 영수증에는 적용하지 않는다.
- 등급 산정 금액은 할인 후 결제 금액이다.

**BR-11 반품 환불 금액**

- 환불 금액 = 그 라인의 결제 금액 ÷ 판매 수량 × 반품 수량, 원 미만 버림.
- 그 라인의 마지막 남은 수량을 반품할 때는 남은 결제 금액을 전부 환불한다. 여러 번 나눠 반품해도 환불 합계가 결제 금액과 같아야 하기 때문이다 (예: 3개 100원 → 33원, 33원, 34원).

**BR-12 판매·반품 중복 저장 방지**

- 판매등록 화면과 반품 창은 열 때 요청 키(UUID)를 하나 만들어 저장 요청에 붙인다.
- 같은 키로 다시 오면 새로 저장하지 않고 처음 저장한 결과를 그대로 돌려준다. 버튼을 두 번 누르거나 네트워크가 다시 보내도 판매·반품은 한 건이다. 반품이 두 번 저장되면 "1개 반품"이 2개가 되므로 반품에도 같은 규칙을 쓴다.
- 같은 키로 다른 내용이 오면 거절한다. 저장이 끝나면 화면은 다음 판매·반품을 위해 새 키를 만든다.
- 저장 위치와 방식은 ADR-006, 03-api.md 4.1·4.2.

**BR-13 가족 구성원**

- 구성원은 고객이 아니다. 전화번호·동의·등급·로그인이 없고, 대표 고객 아래 기록이다.
- 판매·등급·구매이력은 대표 고객 하나에 쌓인다. 그래서 가족 실적은 따로 합산 규칙 없이 대표 고객의 실적이 된다.
- 이름은 실명 대신 호칭으로 받는다. CRM에는 아이 이름이 필요 없고, 만 14세 미만의 개인정보는 법정대리인 동의 등 따질 것이 많기 때문이다. 동의 문구의 수집 항목에 가족 구성원 정보(호칭, 관계, 사이즈)를 적는다 (BR-08).
- 사이즈 목록은 구성원 성별로 정한다(고객과 같은 규칙, REG-01). 자녀는 아동 의류 사이즈(4·6·8·10)도 고를 수 있다. 아동 신발은 다루지 않는다 (02-erd.md 3.2).
- 착용자: 판매 라인마다 구성원을 고를 수 있다(선택). 판매 기록에는 호칭을 복사해 두어, 구성원을 지우거나 호칭을 바꿔도 과거 영수증은 그대로다. 비회원 판매에는 고를 수 없다.
- 콜리스트 가족 필터: 고른 관계의 구성원이 있는 고객만 보여준다 (예: 자녀가 있는 고객).

## 10. 리스크

- **범위 확장**: 새 아이디어는 먼저 '다음'이나 '나중' 칸에 적고, MVP가 끝난 뒤 판단한다.
- **시간**: 추정 소요가 가용 시간 상한에 가깝다. 밀리면 아래 순서로 줄인다.
  1. 판매 시 착용자 선택(CUS-05 일부)을 다음으로 미룬다. 구성원 관리와 가족 필터는 남기고, 판매 라인의 착용자 칸만 뺀다.
  2. QR 등록(REG-03)을 다음으로 미룬다. 키오스크와 직원 대리 등록이 같은 폼이라 기능 공백은 작다.
  3. 등급 기준 화면을 Swagger로 대체한다.
  4. 직원 관리 화면을 Swagger와 시드 데이터로 대체한다.
- **무료 서버의 잠자기**: 요청이 없으면 잠드는 무료 서버는 매년 6월 1일 정기 산정·매일 실적 갱신을 놓칠 수 있다.
  - 일일 실적 갱신은 몇 번 돌아도 결과가 같으므로 서버가 시작될 때도 한 번 실행한다.
  - 정기 산정은 1년에 한 번만 돌아야 한다(아무 날에나 돌리면 그날 강등된다). 올해 이미 돌았는지 적어 둘 곳이 지금 ERD에 없다. 1주 차 배포 확인에서 잠드는 서버로 정해지면 실행 기록을 ADR로 추가하고, 그 전까지는 `POST /grade-policy/periodic-runs`로 수동 실행한다.
- **암호화와 검색**: 전화번호를 암호화하면 번호 부분 검색이 안 된다. 검색은 고객명 + 번호 뒷자리 컬럼으로만 한다.
- **공개 등록 페이지 악용**: QR 페이지는 로그인이 없어 허위 등록이 가능하다. MVP는 요청 수 제한으로 막고, SMS 인증은 다음 단계에서 더한다.

# ERD 개념·논리 점검 (2026-10-24)

> 대상: [02-erd.md](02-erd.md) (테이블 24개). 기준: [01-requirements.md](01-requirements.md), [03-api.md](03-api.md), [decisions.md](decisions.md), [04-architecture.md](04-architecture.md).
> 범위: 개념·논리(테이블, 관계, 키, 모듈, 일부러 중복한 이유). 타입·길이·인덱스 같은 물리 항목은 개발하면서 `schema.sql`에서 다듬는다.

## 2. 시나리오 따라가기

가상 데이터로 한 단계씩 행을 적어 봤다. 막힌 곳만 적는다.

| # | 시나리오 | 막힌 곳 |
| --- | --- | --- |
| S1 | QR로 신규 등록 → 첫 판매(메모 포함) → 2일 할 일 | 요약 행을 등록 때 만드나, 첫 판매 때 만드나 (9). 구매 메모의 `recorded_by`를 채울 값이 이벤트에 없다 (10) |
| S2 | 1·2·3을 산 뒤 1 환불, 2를 4·5로 추가 결제 교환, 3 환불 (BR-17의 예) → 다시 4를 6으로 추가 결제 교환 | 원 판매에 교환이 두 번이면 어느 `sale_return`이 어느 새 판매와 짝인지 모른다 (2). 4→6 교환에서 "원 판매당 교환 티켓 1개"를 판단할 칸이 고객 모듈에 없고, 이벤트 순서 키가 S1·S2로 갈린다 (1) |
| S3 | 김하늘(A)로 잘못 연결한 판매를 마감 전에 김하늘(B)로 정정 | A의 구매 기록이 "기록 취소"인지 "반품"인지 구별이 안 돼 A의 마지막 방문일과 "이 매장 고객"이 그대로 남는다 (3). B의 더 최근 구매 할 일이 정정된 옛 구매 할 일로 대체될 수 있다 (밖-2) |
| S4 | 6/1 정기 산정 → 6/10 지난 시즌 판매 반품 → 7/1 확정 | 등급이 C → C로 그대로인 고객은 이력이 없어 "25/26 시즌 · 40점" 근거를 보여줄 수 없다 (4) |
| S5 | 메인 매니저 퇴사 → 매장 계정으로 이관 → 새 메인 등록, 같은 날 마감 → 본사가 다시 열기 → 다시 마감 | 본사 두 명이 동시에 메인을 등록하면 둘 다 들어간다 (7). 다시 연 뒤에도 마감 행이 남아 "행이 있으면 잠김" 규칙과 어긋나고, 다시 마감하는 방법이 없다 (8) |
| S6 | 매장 노트북과 매장폰에서 같은 판매의 마지막 1개를 동시에 반품 | 요청 키가 달라 UNIQUE로 안 막히고, 둘 다 "남은 1개"를 읽어 2개가 반품된다 (5) |

## 3. 규칙 체크

### ③ 모듈 경계 (ADR-001·003·012, 04 3장)

- 모듈 사이 관계는 모두 점선(ID만)이다. 실선(FK)은 같은 모듈 안에만 있다. ✓
- 새 테이블 3개의 주인: `staff_notification`(common), `store_day_close`(sales), `grade_discount`(customer). 쓰는 쪽과 맞다. ✓
- 고객 모듈은 판매 테이블을 읽지 않는다. 구매이력은 판매 모듈이 제공한다. ✓
- **본사 매장 목록(`GET /stores`, common)이 오늘 판매 수·마감 여부를 보여주려면 판매 모듈을 불러야 해서 common → sales 의존이 생긴다 (6).**

### ④ DB가 지켜야 할 유일·필수 규칙 (ADR-006·017)

| 규칙 | 키 | 결과 |
| --- | --- | --- |
| 영수증 번호 | `UNIQUE(receipt_no)` + 채번 행 잠금 | ✓ |
| 판매·반품 같은 요청 | `UNIQUE(idempotency_key)` 2개 | ✓ |
| 같은 전화번호 | `UNIQUE(phone_hash)` | ✓ |
| 같은 판매 라인 두 번 적재 | `UNIQUE(sale_line_id)` | ✓ |
| 같은 이벤트 두 번 처리 | `processed_event` PK | ✓ |
| 매장 코드·로그인 ID·직원 코드·품번·기준 버전 | 각각 UK | ✓ |
| 매장·날짜마다 마감 1행 | PK(`store_id`, `business_date`) | ✓ |
| 같은 상품의 색상·사이즈 | `UNIQUE(product_id, color, size)` | △ 3.2 본문에만 있고 4장 표에 없다 (13) |

| 남은 수량보다 많이 반품하지 않기 | UNIQUE로 못 막음 | △ 5 |

| 중복 | 원본 | 언제 맞추나 | 틀어지면 | 결과 |
| --- | --- | --- | --- | --- |

| `customer_summary` | `customer_purchase` + 등급 기준 | 판매 이벤트, 정기 산정 | 적혀 있지 않다 | △ 12 |

## 4. 앞서 한 말 정정

ERD 점검 이유를 설명하며 "'매장·날짜마다 마감 1행'은 UNIQUE 표시가 없다"고 예를 들었는데 틀렸다. `store_day_close`는 PK가 (`store_id`, `business_date`)라 이미 막혀 있다.

## 5. 찾은 것

| # | 중요도 | 문제 | 추천 | 바뀌는 칸 |
| --- | --- | --- | --- | --- |
| 1 | 높음 | 교환·정정이 이어질 때(S1 → 교환 S2 → 다시 교환 S3) **처음 판매** 기준이 없다. ① 고객 모듈이 "원 판매당 교환 티켓 최대 1개"(BR-17)를 판단할 칸이 `customer_purchase`에 없다. 이벤트의 `originSaleId`를 받아도 저장할 곳이 없고, 판매 테이블은 읽을 수 없다(ADR-003). ② S3 이벤트의 순서 키는 S2, S2 이벤트는 S1이라 순서 묶음이 갈린다(ADR-007·022). ③ 원 판매를 바로 앞 판매로 보면, 추가 결제 교환을 반복할 때마다 티켓이 는다 | 판매에 처음 판매 ID를 두고, 이벤트 순서 키와 교환 티켓 한도를 모두 처음 판매 기준으로 한다 | `sale.root_sale_id`(처음 판매면 자기 ID), outbox `aggregate_id` = root, 이벤트 `rootSaleId`(추가라 v1 유지), `customer_purchase.root_sale_id`. ADR-022 변경 |
| 2 | 중간 | 교환에서 **돌려받은 라인(`sale_return`)과 새 판매의 짝**을 알 수 없다. 한 판매에 교환이 두 번이면 영수증 상세(SAL-05)의 교환 내역, `extraPaid`, 같은 키 재전송 응답(BR-12)을 만들 수 없다. 정정은 판매당 한 번뿐이라 원 판매로 찾을 수 있지만, 교환은 여러 번 할 수 있어 찾을 수 없다 | 반품 행에 새 판매 ID를 두고, 한 요청으로 생긴 행은 같은 `Idempotency-Key`를 갖는다고 정한다 | `sale_return.new_sale_id`(교환·정정일 때). ADR-006 변경(교환: 반품 행 + 새 판매, 정정: VOID 행 + 새 판매, 기록 취소: VOID 행) |
| 3 | 중간 | 고객 모듈에 **기록 취소 표시**가 없다. VOID를 "없던 구매"로 처리한다고만 있고 지울지 표시할지 정하지 않았다. `returned_qty`만 채우면 반품과 구별이 안 돼, 잘못 연결한 고객(S3)의 마지막 방문일(BR-09)과 "이 매장 고객"(CAL-01)이 남는다 | 행은 지우지 않고 기록 취소된 수량을 따로 적는다(02 5장 #5 "이력이 남는다"와 같은 원칙). 기록 취소는 없던 일이라 방문일·매장 고객·품목 필터에서 빼고, 반품은 있었던 일이라 금액·티켓에서만 뺀다 | `customer_purchase.voided_qty`(나간 수량 `returned_qty` 중 기록 취소분). 처음엔 `voided_at`으로 적었다가, 일부 반품 뒤 나머지를 기록 취소하는 경우를 담으려고 수량 칸으로 바꿨다. 반품·교환·기록 취소 때 방문일도 다시 계산한다고 3.4에 적기 |

### 받아들인 것 (고치지 않음)

- 매장이 "오늘 판매 마감"을 누르는 순간 같이 저장 중이던 판매는 몇 ms 차이로 마감 뒤에 들어갈 수 있다. 같은 날 판매라 피해가 없어 막지 않는다.
- 같은 구매 건 ID가 정정으로 두 고객(A, B)에 걸칠 수 있다. 티켓·금액은 고객별로 세므로 문제없다.
- 상품에서 사이즈·색상을 빼 SKU 행이 지워지면 옛 판매 라인의 `sku_id`는 없는 SKU를 가리킨다. 판매 라인은 스냅샷이라 화면에 영향이 없다.

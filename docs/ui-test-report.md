## 3. 판매 기록 30초 측정 (NFR-08a)

**확인 필요: 사람이 직접 잰 값은 사용자가 재야 한다.** 이 세션의 자동 입력은 사람보다 훨씬 빠르고(타이핑·고르기 시간이 없음), 가짜 API 응답 지연이 150~300ms로 고정이라 아래 값은 **하한(가장 빠르게 해도 이만큼은 걸림)**이다.

시도한 것: 브라우저에서 스크립트로 `판매 사원 → 고객 → 상품 → 저장`을 이어서 눌렀다. 드롭다운 열림·닫힘을 기다리는 부분에서 요소 선택이 흔들려 5번 반복 측정은 **끝까지 돌리지 못했다**. 얻은 값:

| 단계 | 조작 | 자동 입력 시간 | 05 예상 |
| --- | --- | --- | --- |
| 판매 사원 | 클릭 2 (열기 + 맨 위 직원) | 약 0.1초(고정 대기 제외 불가, 측정 불안정) | 2초 |
| 고객 | 키 5 (이름 3글자 + Enter 2) | 약 0.35초 (가짜 응답 지연 포함) | 6초 |
| 상품 | 키 4(검색어·Enter 2번) + 클릭 5(색상 2, 사이즈 2, 담기 1) | 측정 못 함 | 9초 |
| 결제 금액 | 기본값 확인(조작 0) | 0 | 3초 |
| 저장 | 키 2 (Ctrl+Enter, Enter) | 측정 못 함 | 3초 |

**조작 수** (사람이 해야 하는 일): 클릭 약 9 + 키 약 13 = **약 22번**. 05의 예상 23초는 한 번에 1초 안팎으로 계산한 것이라, 조작 수로는 맞는 규모다. 시스템 몫(가짜 응답 지연)은 고객 검색 + 고객 정보 + 상품 검색 + 저장으로 **약 0.9초**다. 실서버에서는 네트워크 시간이 더해진다.

**다음 측정**: ① 사용자가 노트북으로 5번 재서 중앙값을 적는다(12단계 최종 측정 전에 한 번). ② 12단계에서 실서버로 다시 잰다. 30초를 넘으면 단계별로 줄일 곳을 찾는다(예: 판매 사원 직전 직원 자동 맨 위는 이미 있음).

## 8. 이 결과서의 한계

- "이전 PR 확인"과 "미확인"은 이번에 다시 눌러 보지 못한 항목이다. 12단계에서 실제 API로 한 번에 다시 돌린다.
- 가짜 데이터는 응답이 빠르고 항상 성공하므로, 에러·느린 네트워크 항목은 12단계에서 봐야 한다.
- 자동 입력으로는 "눈에 보이는 안내가 알아보기 쉬운지" 같은 사용성을 판단할 수 없다. 사용자 확인이 필요하다.

> 작성: 2026-11-18 · 총괄 세션 · 상태: **확정 (2026-11-18 사용자 승인)**
> 확정되면 `docs/sessions.md`로 올리고 `CLAUDE.md`에서 이 문서를 가리킨다. 세션 ID 같은 이 컴퓨터에만 있는 값은 레포가 아니라 프로젝트 메모에 둔다.
> 변경: 2026-11-18 검토 방식(1.4): 기획을 테스트로 고정하고 CI가 확인, 총괄은 범위·결정·보안만 본다. 완료 기준 ID를 먼저 적는다 (1.2·1.3).

## 0. 한 장 요약

- 작업은 **분야 세션 4개**(문서·백엔드·화면·배포)가 하고, **총괄 세션**은 분야를 넘는 일(계획·우선순위, 세션 간 조율, 분야를 넘는 변경 검토)만 맡는다.
- 흐름: 사용자 → 총괄 → 분야 세션 → (분야 안의 일) 그 세션에서 사용자에게 직접 커밋 확인 → 총괄에 3줄 보고. 분야를 넘는 변경만 커밋 전에 총괄 검토를 거친다 (1.2).
- 토큰 아끼기 규칙은 1.8.
- 남은 기간: 11/19 ~ 12/09, **3주 × 주 20시간 = 약 60시간**.
- 남은 일(추정): 백엔드 Must만 약 72시간 + 화면 연동 약 10시간 + 배포 약 7시간 + 마무리 문서 약 4시간 = **약 93시간**. 줄일 수 있는 항목을 다 빼도 **약 33시간이 모자란다** (3장).
- 정한 것 (3.2): **D1** 각 분야 세션이 그 분야의 개발자로서 자기 작업 계획을 세우고 코드 초안을 쓴다. 총괄이 계획을 판단해 사용자에게 보고한다. **D2** 서버가 없는 화면은 사용자가 흐름을 보거나 피그마로 옮기는 참고용이다. **D3** 방문 예약·재연락 알림은 **웹 푸시까지** 만든다.
- 4장의 분야별 계획과 5장 일정은 **총괄이 쓴 출발점**이다. 각 분야 세션이 이것을 바탕으로 자기 계획을 다시 세워 총괄에 낸다 (1.2).

## 1. 공통 규칙 (모든 세션)

### 1.1 역할

| 세션 | 맡는 일 | 폴더 · 브랜치 |
| --- | --- | --- |
| **총괄** | 계획·우선순위, 세션 간 조율, 분야를 넘는 변경 검토, 분야를 넘는 결정의 사용자 승인 받기, 매일 보고 | 코드 수정 안 함. 각 세션 폴더를 읽기만 |
| **문서** | `docs/`, `README.md`, `CLAUDE.md`, wbs·worklog 갱신, 결정 기록(01 8장, ADR) | 기본 폴더, `main`에 바로 커밋 |
| **백엔드** | `backend/`, `schema.sql`, compose의 `db` 서비스, `backend-ci` | 자기 워크트리, `feat/B…` → PR |
| **화면** | `frontend/` (단, `vite.config.js`의 배포 설정은 배포 세션과 상의), `frontend-ci` | 자기 워크트리, `feat/F…` → PR |
| **배포** | `Dockerfile`, k3s 매니페스트, `Jenkinsfile`, `.github/workflows/pages.yml`, Oracle VM (ADR-037) | 자기 워크트리, `chore/…` → PR |

**같이 쓰는 파일**: `docker-compose.yml`(로컬 개발용, 백엔드 주인 · 배포는 손대지 않음), `frontend/vite.config.js`(화면 `proxy` · 배포 `base`), `.github/workflows/*-ci.yml`(각 분야). 남의 칸을 고쳐야 하면 **먼저 총괄에 알리고**, 총괄이 그 분야 세션에 전한다.

### 1.2 일하는 순서 (분야 세션)

1. **시작**: `git fetch` 후 `main` 최신에서 작업 브랜치를 만든다. 다른 세션 PR이 합쳐졌다는 소식을 들으면 `main`을 받아 브랜치에 반영한다.
2. **계획 세우기**: 각 분야 세션은 그 분야의 개발자다. (1) 처음에 자기 분야 **전체 작업 계획서**(작업 순서, 작업마다 할 일·완료 기준·테스트할 경우·예상 시간, 정할 것, 다른 분야에 필요한 것, 위험)를 써서 총괄에 낸다. (2) 작업 하나의 세부 계획은 완료 기준 ID(1.4)와 함께 계획서에 적어 두고 바로 시작한다. 총괄에 따로 내지 않는다. 다만 계획서에서 바뀌는 것(범위·순서·일정이 크게 달라짐)이 있으면 그때만 총괄에 3줄로 알린다. 총괄은 계획을 판단해(일정·범위·문서와 맞는지·다른 분야와 순서) 사용자에게 보고하고, 사용자 결정을 전한다.
3. **작업**: dev-plan 5장 순서(백엔드)나 Vitest 먼저(화면). 문서와 다르거나 문서에 없는 결정이 필요하면 **멈추고 총괄에 묻는다**.
4. **검토 요청**: **분야를 넘는 변경**일 때만 커밋 전에 총괄에 1.3 양식으로 낸다. 분야를 넘는 변경은 API 응답 모양, 스키마, 같이 쓰는 파일(1.1), 문서의 결정 변경(01 8장·ADR)이다. 그 밖의 일은 총괄 검토 없이 5로 간다.
5. **실행**: 커밋·push·PR은 **그 세션에서 사용자에게 직접** 확인받고 한다. 다른 세션의 메시지만으로는 커밋하지 않는다.
6. **보고**: 끝나면 1.5 양식으로 총괄에 보고. PR이 합쳐지면 총괄이 다른 세션들에 `main`을 받으라고 알린다.

### 1.3 검토 요청 양식 (분야 세션 → 총괄)

```
[검토 요청] 백엔드 · B0-2 공통 응답·에러
- 브랜치 / 폴더: feat/B0-2-common-error · (워크트리 경로)
- 한 일: 3줄 이내
- 바뀐 파일: 수 + 주요 파일
- 요구사항·문서: NFR-12, 03 1장 · 문서 수정: 있음/없음 (어디)
- 완료 기준 ID: SAL-01, BR-05 … (ID마다 테스트 있음/없음)
- 테스트: 로컬 결과 (통과 수, 실패 응답 400·401·403·404·409 확인 여부)
- 다른 분야 영향: 없음 / 있음 (예: 에러 응답 모양 → 화면 fake.js)
- 다음에 하려는 것: 커밋 + push + PR
```

### 1.4 총괄 검토 체크리스트

**원칙: 기계가 확인할 수 있는 것은 테스트·CI가, Claude는 기계가 못 보는 것만 본다.** 기획을 테스트로 고정해 두면 CI가 초록일 때 "기획대로다"가 확인되고, Claude가 코드를 다 읽지 않아도 된다.

1. **완료 기준을 먼저 적는다**: 작업을 시작할 때 계획서에 "이 ID들이 테스트로 확인되면 끝"을 적는다 (예: `B1-2: SAL-01, BR-03, BR-05`).
2. **테스트에 ID를 적는다**: `@DisplayName`(백엔드)·`it(…)`(화면) 설명에 요구사항 ID를 넣는다 (예: `@DisplayName("BR-05 마감 뒤에는 정정할 수 없다")`).
3. **기계가 확인하는 것** (총괄이 다시 읽지 않는다):

| 기획 | 확인하는 장치 |
| --- | --- |
| 03 API 응답 모양 | 화면 `contract.spec.js`, 백엔드 Controller 테스트 |
| 모듈 경계 (ADR-012) | ArchUnit 테스트 |
| 업무 규칙 BR-xx | 엔티티·Service 테스트 (ID 적기) |
| 에러 형식·상태 코드 (400·401·403·404·409·201) | Controller 테스트 |
| 스키마 (02) | Testcontainers MariaDB로 `schema.sql` 실제 실행 |
| 형식 | `backend-ci`·`frontend-ci` (eslint·prettier·테스트) |

4. **총괄이 하는 일**: (1) CI 통과 확인, (2) 완료 기준의 ID마다 테스트가 있는지 `grep`으로 대조, (3) 아래 표에서 기계가 못 보는 것(범위·결정·보안)만 해당 부분을 골라 본다.
5. **깊은 검토는 PR 때 한 번**: 작업 중간 확인은 테스트에 맡긴다. 큰 PR(파일 20개 넘음, 또는 돈·권한·마감 규칙)은 PR 단계에서 `/code-review`를 한 번 돌린다.

아래 표 중 테스트로 확인되는 칸(규칙·테스트·다른 분야)은 CI 결과로 갈음하고, 범위·문서 결정·보안을 중심으로 본다.

| 볼 것 | 확인 |
| --- | --- |
| 범위 | 그 세션이 맡은 파일만 고쳤나. 요청 안 한 기능을 더하지 않았나 |
| 문서 | 01~05·ADR과 맞나. 바뀐 결정은 같은 PR에 문서도 고쳤나(00~03은 `> 변경:` 줄, 결정은 8장·ADR) |
| 규칙 | CLAUDE.md: DTO는 record + `from()`, 엔티티 롬복 제한, 모듈 경계(다른 모듈 `api`만), 커밋 형식 `feat:`…, 브랜치에 작업 ID |
| 테스트 | TDD 순서, `@DisplayName` 한글 + `should_…_when_…`, 실패 응답·201 확인, DB 테스트는 Testcontainers MariaDB, 화면 계산은 Vitest |
| 다른 분야 | API 응답 모양이 03과 화면 `api/*.js` 가짜 응답과 같은가. 스키마 변경이 02와 같은가 |
| 보안 | 비밀 값·실제 고객 데이터 없음(NFR-06·07), 로그에 전화번호·이름 없음(NFR-04b) |
| 진행 | wbs 상태와 worklog 시간을 문서 세션에 알렸나 |

총괄은 먼저 `git -C <워크트리> diff --stat main...`으로 바뀐 파일을 보고, 분야를 넘는 부분(API 모양·스키마·같이 쓰는 파일·결정)만 골라 읽는다. 전체 diff를 다 읽지 않는다. 문제가 없으면 그 세션에 "검토 끝, 문제 없음"을 보내고, 커밋 확인은 그 세션이 사용자에게 직접 받는다.

### 1.5 보고 양식 (분야 세션 → 총괄 → 사용자)

```
[완료] 백엔드 · B0-2 → PR #8 (CI 통과/진행 중)
- 된 것 / 안 된 것 / 확인 못 한 것
- 쓴 시간: 3.5h (worklog용)
- 다음: B0-6
```

보고는 이 3줄을 넘기지 않는다. 자세한 내용(테스트 출력, 파일 목록, 막힌 곳 분석)은 공유 노트 폴더의 그 분야 파일에 적고, 보고에는 파일 이름만 쓴다. 총괄은 꼭 필요할 때만 그 파일을 연다.

### 1.6 승인 규칙

- 커밋·push·PR 합치기·배포·공개·문서의 결정 변경은 **사용자 승인**이 필요하다(CLAUDE.md).
  - 커밋·push·PR은 그 일을 하는 세션에서 사용자에게 **직접** 받는다 (안전 규칙상 어차피 그 세션에서 확인해야 하므로, 총괄이 한 번 더 중계하지 않는다).
  - 분야를 넘는 결정(우선순위, 범위 줄이기, 문서의 결정 변경)은 총괄이 사용자에게 받아 **사용자 말을 그대로 인용해** 전한다.
- 총괄 혼자 승인할 수 있는 것: 작업 순서 조정, 검토 의견("이 부분 고쳐 줘"), `main` 받기 안내.
- 사용자가 분야 세션에 직접 지시하면 그 세션은 따르고, 끝나면 총괄에 보고한다.

### 1.7 총괄의 정기 일

- **매일 끝날 때**: 오늘 한 일·쓴 시간·내일 할 일을 사용자에게 한 번에 보고하고, 문서 세션에 wbs "지금" 줄과 worklog 갱신을 맡긴다.
- **매주 화요일**(주 끝): 남은 시간과 남은 일을 다시 계산한다. 계획보다 20% 넘게 밀리면 3장의 줄이는 순서를 바로 사용자에게 제안한다.

### 1.8 토큰 아끼기

세션마다 대화가 길수록, 그리고 큰 파일을 많이 읽을수록 한 턴의 비용이 커진다. 5시간 사용 한도를 넘지 않게 아래를 지킨다.

| 규칙 | 할 일 |
| --- | --- |
| 총괄을 덜 깨우기 | 분야 세션은 끝났을 때와 막혔을 때만 총괄에 보낸다. "시작해요", "이해했어요" 같은 중간 메시지는 보내지 않는다. 총괄은 받은 3줄로 판단하고, 그 세션 대화 기록을 다시 읽으러 가지 않는다 |
| 필요한 부분만 읽기 | 큰 문서(01·03·05·dev-plan)는 통째로 읽지 않고 ID(`SAL-01`, `BR-05`, `4.12`)로 찾아 그 부분만 읽는다. 자기 분야 밖 폴더는 읽지 않는다. 테스트·빌드 로그는 실패한 줄 근처만 본다 |
| 같은 것을 다시 읽지 않기 | 이미 읽은 문서를 다시 읽지 않는다. 계획·결정·진행은 공유 노트 폴더의 자기 계획서에 적어 두고, 새 세션은 그 파일부터 읽는다 |
| 세션 하나에 일 하나 | 작업(작업 ID 하나, 또는 PR 하나)이 끝나면 그 대화를 이어 가지 않는다. 계획서에 다음 할 일을 적고, 사용자가 `/clear`하거나 새 세션을 연다. 대화가 길어졌는데 일이 남았으면 사용자에게 `/compact`를 권한다 (Claude가 스스로 실행할 수 없다) |
| 동시에 도는 세션 줄이기 | 코드 세션(백엔드·화면·배포)은 동시에 2개까지만 돌린다. 나머지는 계획서에 다음 할 일을 적어 두고 쉰다 |
| 모델 | 코드 세션과 문서 세션은 Sonnet, 총괄만 Opus. 문서 세션이 큰 결정(ADR·업무 규칙)을 써야 하면 총괄이 판단해 넘긴다 |
| 짧게 쓰기 | 보고는 1.5의 3줄, 검토 요청은 1.3 양식. 코드·로그를 메시지에 붙이지 않고 파일 경로와 줄 번호로 가리킨다 |
| 규칙 파일은 짧게 | `CLAUDE.md`는 모든 세션이 매 턴 읽는다. 세션 운영 규칙은 이 문서에 두고 `CLAUDE.md`에는 이 문서를 가리키는 한 줄만 둔다 |

사용량은 `/usage`로 본다. 한도에 걸려 세션이 멈추면 총괄은 한도가 풀린 뒤 멈춘 일만 한 줄로 다시 보낸다.

### 3.2 사용자가 정할 것

**D1. 모자란 시간을 어떻게 메울까** → **A로 결정 (2026-11-18)**: 각 분야 세션은 그 분야의 개발자로서 직접 일하는 방법과 순서를 계획하고 코드 초안을 쓴다. 총괄은 그 계획을 판단해 사용자에게 보고한다. 테스트할 경우는 사용자와 같이 정하고, 핵심 로직(등급 계산기 B3-2, outbox B2-4)은 사용자가 직접 쓸지 작업 때 묻는다.

| 안 | 내용 | 결과 |
| --- | --- | --- |
| **A (추천)** | 백엔드 작업마다 **테스트할 경우는 사용자와 같이 정하고, 코드 초안은 세션이 쓰고, 사용자는 읽고 설명을 들은 뒤 승인**한다. 핵심 로직(등급 계산기 B3-2, outbox B2-4)만 사용자가 직접 쓴다 | 속도 약 1.5~2배. "개발 순서 익히기" 목표는 테스트·검토로 유지 |
| B | 지금처럼 사용자가 직접 쓰고 세션은 설명·검토만 | 12/09에 핵심 흐름(판매 → 등급 → 오늘 할 일)까지만 될 가능성이 큼 |
| C | 마감을 1~2주 늦춘다 | 범위 유지 |

**D2. 화면만 있고 서버는 안 만드는 기능** → **결정 (2026-11-18)**: 그 화면들(키오스크·QR, 상품 엑셀, 교환·정정, 가족 편집, 설정 고치기, 본사 직원 등록, 알림 설정 등)은 **사용자가 흐름을 보거나 피그마로 옮겨 코드를 뽑기 위한 참고용**이다. 서버를 만들지 않고, 실서버 연결·공개 대상이 아니다. 실서버 화면에서는 메뉴를 숨긴다. 화면 데모(GitHub Pages)를 공개할지는 배포 세션 계획에서 따로 정한다.

(검토 때 낸 추천안, 참고) (1) GitHub Pages 화면 데모는 지금처럼 **모든 화면을 가짜 데이터로** 보여준다(누구나 눌러 봄). (2) 실제 서버는 **Must 흐름만** 연결하고, 서버가 없는 메뉴(키오스크·엑셀·교환·정정·가족 편집·설정 고치기·직원 등록 화면)는 숨기거나 "데모에서만" 표시한다. README에 둘을 나눠 설명한다.

**D3. 방문 예약·재연락 알림(11/13 추가)은 어디까지** → **웹 푸시까지로 결정 (2026-11-18)**: VISIT·RECALL 할 일(오늘 할 일), 아침 9시 묶음 알림(알림함 `staff_notification`), 직원 알림 설정(시점), 웹 푸시(서비스 워커·VAPID·`push_subscription`)까지 서버에서 만든다. Kafka·Redis는 쓰지 않는다(서버 하나, CLAUDE.md). SSE는 만들지 않는다(화면을 열거나 옮길 때 알림함을 다시 읽음, W6). 추가 시간 약 7.5~9.5h(할 일 1.5 + 묶음 알림·설정 2 + 웹 푸시 4~6)라 다른 항목에서 그만큼 줄여야 한다. 웹 푸시는 HTTPS가 있어야 하므로 실서버(k3s Ingress HTTPS) 위에서만 확인된다.
